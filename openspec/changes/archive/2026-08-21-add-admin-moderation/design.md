## Context

前面三個 change 依序留下：行為稽核（`add-chat-observability`）、
檢舉入口（`add-chat-report`）、以及**一條至今沒有任何豁免的守則**
（`chat-message-single-entry`：訊息表只能由其 repository 存取）。

這個 change 把前兩者接起來。**原本以為它會需要那條守則的第一筆豁免，實際上不需要**
——檢舉詳情讀的是 `chat_reports.contentSnapshot`，不是 `chat_messages`
（見「實作過程中的修正」）。

範圍是使用者選定的：**只做狀態流轉**（移除訊息／停權留給後續獨立 change）、
**每次查看被撤回內容都留稽核**。

## Decisions

### D1：只做狀態流轉，不做移除訊息或停權

`PENDING → REVIEWED / DISMISSED`，加一段處理註記。管理員看得到、能標記已處理，
但**不直接動業務資料**。

**為什麼不順手做移除訊息**：它看起來只是「多一個 `deletedAt`」，實際上是三件事：

- 需要新欄位區分「使用者撤回」與「管理員移除」——**兩者對客戶端的語意不同**
  （「已收回」vs「因違規被移除」），共用一個欄位會讓前台無法正確顯示
- 需要推播讓所有人的畫面同步，而那要決定推播內容（說不說原因？）
- 需要自己的稽核與授權，而它的授權來源是 RBAC 而非成員資格

**停權更是獨立主題**：連動 `tokenVersion`（強制登出）、WS 連線斷開、
「停權期間能不能看歷史」——每一項都要決定。

把它們塞進來會讓這個 change 從「讀取與判定」變成「讀取 + 判定 + 兩套處置」，
而處置做錯的代價遠高於做慢。**先讓管理員看得到，再決定他能做什麼。**

### D2：查看檢舉詳情會寫稽核——這是特權路徑的對價

`GET /api/admin/moderation/reports/:id` 回傳內容快照，而快照可能是**已被撤回的訊息**。
每次呼叫都寫一筆 `REPORT_VIEWED` 稽核。

**為什麼查看也要記**：這條路徑的存在理由是「調查需要看到被撤回的內容」。
如果查看不留痕跡，那它與「任何人都看得到」在事後沒有實質區別——
差別只在於誰有權限，而權限可能被誤配、被濫用、或在事後被質疑。
**權力要留下痕跡，否則它就只是一個沒有人在看的開關。**

代價是佇列瀏覽會產生稽核列。因此**只有詳情端點記，列表端點不記**：
列表不回傳內容快照，看不到任何被撤回的東西。這個切分讓稽核量與
「實際看到了敏感內容的次數」對齊，而不是與「點了幾下」對齊。

### D3：列表不含內容快照，詳情才有

列表回傳檢舉的中繼資料（誰檢舉、檢舉誰、理由、時間、狀態），**不含 `contentSnapshot`**。

這不只是為了 D2 的稽核切分，也是為了**讓誤觸的代價變小**：
管理員瀏覽佇列時不會無意間看到一整頁的敏感內容，
而是必須為每一筆做出「我要看這個」的明確動作。

### D4：權限碼分 VIEW 與 EDIT

`BACKEND:MODERATION:VIEW`（查佇列、查詳情、查行為時間軸）與
`BACKEND:MODERATION:EDIT`（狀態流轉）。

分開是因為兩者的風險不同：查看會接觸到敏感內容，判定會改變狀態。
**「能看的人」與「能判的人」在真實團隊裡經常不是同一群**——
客服看得到、只有主管判得了，是常見的配置。

### D5：先立下豁免的標準，即使這次用不到

守則至今零豁免，**而這個 change 也不會新增**（見「實作過程中的修正」）。
但「看得到被撤回內容」的需求遲早會直接落到 `chat_messages` 上（例如查看某人的完整對話），
而那時候的人會有充分的理由趕著加豁免。

**標準要在還不急的時候立好。** 因此現在就要求：與調查相關的豁免，`reason` 必須同時說明：

1. **僅限後台**（`adapter/in/web/admin/` 之下）
2. **需 RBAC 授權**（有 `@Permissions` 裝飾器）
3. **查看留稽核**

**不放寬守則本身。** 放寬（例如「後台目錄整個排除」）會讓下一個後台功能自動獲得
繞過遮蔽的能力，而它可能根本不需要——這次就是最好的例子：
原本以為需要繞過，實際上完全不用。逐筆豁免逐筆說明，是讓白名單不長大的唯一方式。

### D6：行為時間軸是「查某個成員」，不是「查全部稽核」

`GET /api/admin/moderation/members/:memberId/timeline`，而不是一個泛用的
`GET /audit-logs?filter=...`。

調查的問題永遠是「**這個人**做了什麼」——`chat_audit_logs` 的索引
（`memberId, createdAt`）就是為它建的。開一個泛用查詢端點會誘使人用它做
「最近所有動作」這類瀏覽，而那沒有調查價值、卻會掃到全表。

## Open Questions

- **檢舉佇列的排序與優先序**：目前只按時間排序。「被檢舉次數」「檢舉人信譽」
  要不要加權，等有真實佇列再決定——現在猜會猜錯（沿用 `add-chat-report` 的未決項）。
- **`REVIEWED` 之後能不能再改**：目前允許 `REVIEWED ↔ DISMISSED` 互轉（都是終態間的更正），
  但不允許回到 `PENDING`。是否需要「重新開啟」等實際使用再說。
- **稽核與檢舉的保留期限**（第三次出現）：三個 change 都碰到它。
  它已經大到應該獨立成一個 change，而不是繼續掛在 Open Questions。

## 為「處置」預留了什麼

`reviewNote` 是自由文字，因為現在沒有處置動作可選。日後有了移除訊息／停權，
它會變成「處置的補充說明」而非「處置本身」——那時會加 `action` 欄位，
而 `reviewNote` 的語意不需要改。

`reviewedBy` 存的是管理員的 memberId，不建外鍵：稽核性質的欄位要能在帳號被刪除後
仍然存在。

## 實作過程中的修正

### 這個 change 不需要 `chat-message-single-entry` 的豁免

proposal 原本寫「這是第一條看得到被撤回內容的路徑，會建立守則的第一筆豁免」。
實作前一驗證就發現那是錯的：**檢舉詳情讀的是 `chat_reports.contentSnapshot`**，
一張獨立的表，完全不碰 `chat_messages`。

守則因此維持**零豁免**——這比「加一筆有充分理由的豁免」更好。
豁免的檢查仍然照計畫強化（D5），但它現在是**預先立下的標準**而非當下的需要：
真正需要直接讀 `chat_messages` 的後台功能（例如查看某人的完整對話）遲早會出現，
而那時候的人會有充分的理由趕著加。標準要在還不急的時候立好。

這也是 tasks.md 4.3 特地寫成檢查點的原因——**「以為需要」與「確認需要」之間，
應該要有一步驗證**。

### 「列表不含快照」的真正防線是型別，不是 select

tasks.md 3.2 寫「列表的 select 不得包含 `contentSnapshot`，單元測試釘住——
它是最容易『順手 select 全部』的地方」。反向驗證時把 `contentSnapshot: true`
加進 `listSelect`，**e2e 卻沒有變紅**。

原因是投影函式 `toListItem()` 不會把它複製到輸出，所以 API 回應仍然乾淨。
再進一步把它加進投影函式，**TypeScript 直接編譯失敗**——
`ChatReportListItem` 型別裡根本沒有這個欄位。

也就是說：真正的防線是**型別**（列表視圖與詳情視圖是兩個型別），
`select` 只是順手的最佳化，e2e 是最後的背書。這比原本設想的更牢固，
但也意味著 tasks.md 的敘述不準確——記在這裡，免得下一個人以為 select 是防線。

### swagger 不能用 `allOf`

詳情的回應原本用 `allOf` 合併列表欄位與詳情欄位——`swagger:bundle` 與 `swagger:check`
都過，但 `pnpm typecheck` 在 `packages/api-client` 爆掉：openapi-typescript 產出交集型別，
codegen 之後取 `.schema` 失敗。

`swagger:check` 驗的是「產物是不是最新」，不是「產物編不編得過」——兩者是不同的問題。
已改成明列欄位。
