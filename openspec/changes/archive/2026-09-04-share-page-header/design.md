## Context

版面慣例靠人記得維持，而人會抄歪。這支把「記得寫對」換成「沒有可以寫歪的地方」。

## Goals / Non-Goals

**Goals:**

- 列表頁的頁首只有一種寫法。
- 慣例寫進 spec，不再只存在於「看前一頁怎麼寫」。

**Non-Goals:**

- **不加擋版面的守則**（見 D1）。
- **不動明細頁**（見 D2）。
- 不改任何頁面的文案、不改行為。

## Decisions

### D1：用元件取代規則，不寫守則

考慮過加一條「列表頁最外層必須是 `flex flex-col gap-4`」，**沒有採用**：

- 它擋不住**該有差異**的頁面——五個明細頁本來就沒有那層結構。
- 放寬到能容納那些例外之後，就抓不到今天這種偏差了。
- **會誤報的守則會被繞過**，那比沒有更糟（判準見 `openspec/project/testing.md`）。

守則擅長的是「這個字串不該出現」「這兩份清單要一致」這種可精確表達的規則；
版面不是那種形狀。**元件才是這裡對的工具**：沒有可以寫歪的地方，
就不需要有人記得寫對。

⚠️ **代價誠實標記**：元件擋不住「不用它」。有人下次直接手寫 `<header>` 一樣沒東西會紅。
這條慣例因此要寫進 spec——**spec 是給人讀的那一半**，元件是給機器執行的那一半。

### D2：明細頁刻意不納入

五個明細頁（`front-users/detail`、`moderation/report-detail`、
`moderation/member-profile`、`moderation/room-detail`）的頁首是**真的不同形狀**：

```
<header className="flex flex-wrap items-center gap-2">
  {backButton}
  <h1>{動態標題}</h1>
  <span>{徽章}</span>
</header>
```

返回鍵 + 動態標題 + 行內徽章，沒有副標、不是 `justify-between`。

**硬套進 `PageHeader` 需要加 leading slot、關掉副標、改變對齊方式**——
一個同時服務兩種形狀的元件會長出一堆條件分支，
而那正是共用元件開始腐爛的方式。**形狀不同就該是不同的元件。**

如果之後明細頁也想要統一，那是另一支 change 與另一個元件（`DetailHeader`），
不是把這個撐大。

### D3：營運總覽的載入狀態也換

`moderation/dashboard` 有兩處標題：載入中是裸 `<h1>`、載入完成才是完整頁首。
兩處都換成 `PageHeader`（載入中不帶副標）。

**不換的話那頁自己就有兩種寫法**，而「同一頁的兩個狀態長得不一樣」
是使用者實際會看到的閃動。

## Risks / Trade-offs

- **元件擋不住「不用它」**（D1 已標記）。緩解是把慣例寫進 spec。
- **`PageHeader` 之後可能被要求支援更多變體**。判準寫在 D2：
  形狀不同就開新元件，不要加分支。
- **9 處遷移的視覺回歸只能靠人看**。單元測試涵蓋元件本身的三種組合，
  但「遷移後每一頁長得跟以前一樣」沒有自動化的驗證方式——
  這是純結構重構的固有限制，誠實標記。
