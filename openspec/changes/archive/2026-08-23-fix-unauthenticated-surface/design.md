## Context

專案審查報告的 🔴 與部分 🟡。四個問題的共同形狀是**沒有人會主動去看**：
一個預設值、一個永遠不會消失的旗標、一個 `startsWith`、一個沒有開關的掛載。
它們都不會在任何測試裡變紅，也不會在 code review 時顯眼。

逐項驗證過報告的宣稱，**其中一條不成立**：問題 11 說
`NODE_ENV` / `SERVICE_NAME` / `LOG_LEVEL` 不在 envSchema，實際上三個都在
（`validate-env.ts:5, 9, 10`）。真正的情況是 `logger.ts` 直讀 `process.env`
而非 `getEnv()`，理由是初始化順序。那一條移到後續的清理 change，不在本 change 範圍。

## Decisions

### D1：鎖定加時效，而不是加 break-glass 帳號

審查建議「保留一組不受鎖定影響的 break-glass 帳號」。**不採納。**

加了時效之後，它要解決的問題（沒有人能登入去解鎖）已經不存在。
而「有一個帳號永遠不會被鎖」本身是一個新的攻擊面——它會變成暴力破解的唯一目標，
而且沒有任何速率限制擋著它（帳號鎖定正是那個機制）。

用時效的另一個好處是**它不需要任何人記得**。人工解鎖的流程只要一個環節失效
（管理員離職、聯絡方式過期、值班的人沒有 SUPERADMIN），系統就回到原本的死結。

### D2：鎖定到期時必須一併清除失敗計數

這是最容易漏的一步。`recordFailedLogin` 的 Redis 計數器 TTL 是 **1800 秒（30 分鐘）**
（`PrismaAccountLockAdapter.COUNTER_TTL`），而鎖定時效預設 15 分鐘。

只加時效不清計數的話：鎖定 15 分鐘後到期 → 使用者再打錯一次 → 計數器還在 3 →
**立刻重新鎖定**。實際的鎖定時間會變成計數器的 TTL（30 分鐘）而不是設定的 15 分鐘，
而設定的那個數字看起來完全正常。

因此**到期的判定與計數的清除必須發生在同一個地方**。做法是讓
`LoginService` 在確認鎖定已到期時呼叫 `resetFailedLogin(email)` 再繼續，
而不是讓 `isLocked` 偷偷做寫入——一個叫 `isLocked` 的方法有副作用，
是下一個人絕對不會預期的事。

### D3：時效不解決「持續攻擊者可以持續鎖住」，那是另一個機制的職責

要誠實記下這一點：加了時效之後，攻擊者仍然可以每 15 分鐘重新鎖一次。
時效解決的是「**永久且無復原路徑**」，不是「不會被鎖」。

真正對付持續攻擊的是 **per-IP 而非 per-account** 的限制，而那個機制已經存在：
`APPLICATION_IP_BLOCK_THRESHOLD`（預設 5）會把來源 IP 加進黑名單。
分散式攻擊仍然繞得過，但那時的成本已經與一般的 DDoS 同級，不是「知道 email 就能做」。

**不在本 change 擴充 IP 封鎖**：它已經在運作，而改動它需要先有實際的誤判資料。

### D4：`SWAGGER_ENABLED` 的預設值依環境而非固定

固定預設 `true` 會讓忘記設定的 production 裸奔；固定預設 `false` 會讓開發者
第一次跑起來就找不到文件，然後在 issue 裡問。

因此預設值取決於 `NODE_ENV`：production 為 `false`，其餘為 `true`。
這讓「什麼都不設」在兩種環境下都是對的行為，而那是預設值唯一該有的性質。

**同時關掉 `/docs` 與 `/docs-json`**。只關 UI 是最容易犯的錯——
`docs-json` 才是真正有價值的那份（完整結構、可直接餵給工具），
而它沒有介面所以不顯眼。

### D5：`/api/metrics` 只修豁免範圍，不加認證

`startsWith('/api/metrics')` 改成精確比對（去掉 query string 之後）。

**不在這個 change 給它加認證**：它存在的目的是被 Prometheus scrape，
而 scrape 端的憑證設定屬於部署層（綁內網介面、或用反向代理擋）。
在應用層加一組 bearer token 會需要另一套金鑰管理，而那個決定應該連同
部署方式一起做。

本 change 的範圍是「豁免不該比需要的更寬」——那是純粹的程式碼缺陷，與部署無關。

### D6：`DB_PORT` 預設值 3306 → 5432

模板時期是 MySQL，轉 PostgreSQL 時漏掉了這個預設值。

**改預設值是有風險的動作**，但這裡的風險方向是好的：
- 已明確設定 `DB_PORT` 的環境（本機 `.env` 是 5442、compose 是 5432）完全不受影響
- 沒設定的環境現在會去連 3306，那**必然是壞的**——PostgreSQL 不在那個埠上

也就是說，這個改動只可能把「本來就壞的」變成「可能對的」，沒有反向的情況。

### D7：新增守則盯的是「豁免的表面」而非個別路徑

四個問題裡有三個是「某條路徑不需要認證」的變體。與其逐個修，
更值得的是讓**新增一條免認證路徑這件事本身必須表態**。

守則的形狀（見 spec）：`JwtAuthGuard` 裡任何以路徑字串做的豁免、
以及 `main.ts` 裡任何 `app.use()` 掛載的路由，都必須列入 allowlist 並註明理由。
`@Public()` 已經是明示的表態，不在此列。

這條規則要抓的不是今天這三個，是**下一個**——而下一個一樣不會有人在 review 時看見。

## Open Questions

- **鎖定時效 15 分鐘是否合適**：沒有實際的誤鎖資料可以校準。
  15 分鐘的選擇標準是「足以讓自動化攻擊失去效率，又不至於讓真人等到放棄」。
  等有登入失敗的實際分布再調。
- **`/api/metrics` 最終要怎麼保護**：綁內網介面是最乾淨的，
  但那取決於部署形態（目前是單一容器 + 反向代理還是別的）還沒定。

## 為什麼四件事放在同一個 change

它們在程式碼上沒有關聯，放在一起的理由是**驗證方式相同**：
四個都要「用未認證的身分去打，確認打不到 / 打不壞」。
拆成四個 change 會讓同一組 e2e setup 重寫四次，而每一個單獨都小到不值得一個 PR。

塊的切分仍然是獨立的（見 tasks.md），任何一塊都能單獨驗證。
