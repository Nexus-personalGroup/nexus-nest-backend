## Context

後端的審閱能力在 `add-chat-report`、`add-admin-moderation`、`add-admin-message-removal`、
`add-account-suspension` 四個 change 中陸續完成，但**沒有任何介面**。
這個 change 把它接起來，並補上接的時候才發現的兩個後端落差。

前端目前有三個成熟的頁面可循（會員 / 角色 / IP 名單），慣例明確：
DataTable + URL state + `useApiQuery` + 權限驅動顯示。審閱頁**不發明新模式**，
只在一個地方偏離：詳情走獨立路由而非 Dialog（見 D3）。

## Decisions

### D1：email 用批次查詢補，不建外鍵、不做 Prisma relation

`ChatReportRecord` 的 `reporterId` / `targetMemberId` **刻意沒有外鍵**：
檢舉必須在被檢舉者的帳號被刪除之後仍然可以審閱。這個決定不改。

因此補 email 不能用 `include`，而是**一次批次查詢**：收集本頁所有相關的 member id，
`findMany({ where: { id: { in: ids } } })` 取回 `id → email` 的對照，再貼回結果。
一頁 15 筆檢舉最多 30 個 id，一次查完，不是 N+1。

`LoadMemberPort` 已經有 `findActiveMemberIds(ids)` 這個批次慣例，新方法沿用同樣的形狀。

**email 必須可為 `null`。** 帳號被刪除時查不到，回 `null` 而非省略欄位或回空字串：
- 省略欄位會讓前端分不出「後端沒給」與「真的沒有」
- 空字串會被誤render成空白格，看起來像資料壞了

前端遇到 `null` 顯示「已刪除的帳號」加上可複製的 id 尾碼。

**為什麼是 email 不是暱稱**：審閱要的是**唯一可辨識**的身分。
`member`（暱稱）可以重複也可以改，而審閱紀錄要能在事後對得起來。

### D2：詳情補的是 `targetMessageRemovedAt`，不是布林

回時間戳而非 `isRemoved: boolean`，理由是**布林會讓「何時被移除」永遠拿不到**，
而那是審閱紀錄的一部分。時間戳能推得出布林，反之不行。
命名帶 `targetMessage` 前綴是為了避免與檢舉自身的 `reviewedAt` 混淆——
兩者在詳情頁會同時出現。

**不回 `removedBy`**：那是稽核紀錄該回答的問題，而時間軸端點已經在回答它。
在詳情裡再放一份會產生兩個可能不一致的來源。

**刻意不處理的競態**：兩個管理員同時開同一筆檢舉，A 移除訊息後 B 的畫面仍是舊的，
B 按「移除」會收到 204（移除是冪等的，見 `api-moderation` 既有需求）。
結果正確，只是 B 少看到一次狀態變化——處置動作全部冪等正是為了讓這種情況無害。
加輪詢或 WS 推播來消除它，代價遠大於收益。

### D3：詳情走獨立路由 `/moderation/reports/:reportId`，不是 Dialog

會員與角色的詳情都用 Dialog + URL query（`?view=<id>`）。審閱詳情偏離這個慣例，
因為它**不是一個表單，是一個工作區**：內容快照、檢舉理由、被檢舉者的行為時間軸、
四個處置動作、判定表單，全部要同時在畫面上。塞進 Dialog 會變成需要捲動的擁擠彈窗。

獨立路由還有兩個實際好處：網址可以直接貼給同事看同一筆檢舉，
以及**瀏覽器的返回鍵回到佇列**——審閱是「看一筆、回列表、看下一筆」的動線，
Dialog 的關閉行為在這個動線上比返回鍵難用。

代價是多一個路由層級與一次額外的載入。可接受。

### D4：查看詳情會寫稽核，所以前端不得預先載入

詳情端點**每次呼叫都寫一筆 `REPORT_VIEWED` 稽核**——那是刻意的設計，
稽核量要與「實際看到敏感內容的次數」對齊。

因此前端有兩件事不能做：

- **不得在佇列頁 prefetch 詳情**（hover 預載是常見的體驗優化，這裡會製造假稽核）
- **不得因為元件重繪就重打**——`useApiQuery` 的預設已經是 `refetchOnWindowFocus: false`，
  但 staleTime 要明確設定，避免切分頁回來又記一筆

這條規則寫進 spec，因為它是**看程式碼看不出來的**：一個 prefetch 只有一行，
而它會讓稽核紀錄失去意義，且沒有任何測試會變紅。

### D5：處置動作全部走「確認後執行」，不做 optimistic update

會員列表的狀態切換用 optimistic update（切換 Switch 立即反應）。
審閱的處置**刻意不這樣做**：移除訊息、停權都是對真人有實質影響的動作，
而 optimistic update 的本質是「先假設成功」。假設錯誤時使用者已經看到成功的畫面了。

每個處置動作都是：確認對話框 → 執行 → 成功後 invalidate 重查。
慢一點，但審閱不是需要手速的工作。

### D6：時間軸在詳情頁內嵌，分頁但不做無限捲動

時間軸用既有的 `GET /moderation/members/:memberId/timeline`，顯示被檢舉者的行為。
**放在詳情頁側邊而非另開頁面**：判斷「初犯還是慣犯」是做判定的當下就要有的資訊，
需要跳頁去看的資訊在實務上等於沒有。

只顯示第一頁（預設 15 筆）加一個「查看更多」的分頁控制，不做無限捲動——
審閱要的是最近的行為，而不是把整個歷史讀完。

## Open Questions

- **檢舉佇列要不要顯示「同一人被檢舉幾次」**：這是很強的優先序訊號，
  schema 也有 `idx_chat_reports_target_member` 支援。但它需要一個 group by 查詢，
  且「幾次」的時間範圍要定義（全部？最近 30 天？）。先不做，
  等實際用過佇列之後再看它是不是真的需要——現在猜會猜錯時間範圍。
- **判定後要不要通知檢舉人**：需要通知機制，而通知在 Phase 1 範圍外。

## 為什麼現在不做 SSE 儀表板

`ui-moderation` 與儀表板沒有共用元件：一個是表格與表單，一個是即時數字與圖表。
綁在一起會讓這個 change 的驗收變成「兩個不相干的東西都要對」。
儀表板另開 change，那時可以專心處理它自己的問題（SSE 連線管理、重連、數字的更新頻率）。
