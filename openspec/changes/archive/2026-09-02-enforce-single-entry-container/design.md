## Context

`add-nginx-proxy-and-containerised-e2e` 做了 nginx 單一入口，並在
`platform-container-dev` 寫下：

> api 與 web 各自的對外埠 MUST 保留——反向代理是**多一條路**，不是取代既有的兩條。

那句話當時是對的：代理是新東西，還沒被日常使用驗證過，砍掉退路不合理。
一週後代理穩了，那句話變成成本——本 change 把它反轉。

**這份文件的主要工作是解釋反轉的理由**，而不是設計新東西。改動本身只有
compose 幾行、一支守則、三處文件。

## Goals / Non-Goals

**Goals:**

- 容器模式下**只有一個入口**，且這件事有守則守著、不靠自律。
- 反轉的理由留成紀錄——讀到舊 spec 與現況不符的人要找得到中間發生了什麼。

**Non-Goals:**

- **不動 host 模式**（`pnpm docker:deps` + `pnpm dev`）。那是另一種拓撲，
  不是同一件事的替代寫法（見 D3）。
- **不做除錯用的開埠機制**（見 D2）。
- 不碰正式部署——那從一開始就是單一埠，本 change 是讓開發環境跟上。

## Decisions

### D1：反轉「對外埠 MUST 保留」，而不是保留兩條路

上週那條需求的理由是「保守」，不是「兩條路本身有價值」。現在秤兩邊：

| | 留著 | 關掉 |
| --- | --- | --- |
| 代理壞掉時 | 還能工作 | 要修代理才能工作 |
| origin 一致性 | **可選**——走 `:5173` 就繞過了 | 強制 |
| 新人第一次開 | 三個網址要挑一個 | 一個 |

「代理壞掉時還能工作」是唯一的好處，而它同時是壞處：**代理壞掉時你會不知道**，
因為還有兩條路能用。日常都走 `:5173` 的話，代理的設定漂了幾天沒人發現，
下次真的要驗 CORS 時才炸——而那時已經不知道是哪次改動弄壞的。

決定關掉。單一入口的價值來自「沒有第二條路」，留一條備援等於沒做。

**不選「保留但預設關閉、需要時開」**：compose 的 `ports:` 沒有條件語法，
要做只能靠 override 檔或 profile，成本見 D2。

### D2：不做除錯用的開埠逃生門

考慮過 `compose.debug-ports.yml`（override 檔）+ 一支 `pnpm docker:up:ports`。
不做，兩個理由：

1. **逃生門已經存在而且更好**：要直連 api / web 就跑 host 模式，
   那條路本來就是 3000 / 5173，什麼都不用加。
2. **要分辨「nginx 壞了還是 app 壞了」不需要開埠**，一行就夠：

   ```bash
   docker compose exec nginx wget -qO- http://api:3000/api/health
   ```

   從代理容器內部打後端，正好切在兩者中間——比開一個 host 埠更精準地
   回答那個問題（開 host 埠測到的是「host → api」，跳過了代理的網路路徑）。

多一份 override 檔的代價不只是那個檔：`compose-files.spec.ts` 要求每份
`compose*.yml` 都有 script 會啟動它，於是還要多一支 script、多一段 README。
為了一個已經有更好替代品的需求付這些，不划算。

### D3：CORS 從此只由 host 模式覆蓋，這是可接受的

關掉 `:5173` 之後，容器模式變成同源，**CORS 那條路再也不會被走到**。
乍看是失去覆蓋，實際不是：

- 正式環境本來就是單一 origin（後端 `ServeStatic` 吐 SPA），
  所以容器模式現在**比以前更貼近正式**——那正是做代理的目的。
- CORS 仍然由 host 模式覆蓋：`pnpm dev` 是 5173 → 3000，真正的跨 origin。

於是兩種模式各自覆蓋一種拓撲，而不是兩種都覆蓋同一種。這比原本好。

**代價要說清楚**：以後改 CORS 設定的人，在容器模式下改了不會看到任何差別。
`CORS_ORIGIN` 的註解要寫這件事。

### D4：`CORS_ORIGIN` 同時列 `127.0.0.1` 與 `localhost`

README 反覆強調用 `127.0.0.1`（macOS 的 `localhost` 會優先解析成 IPv6 `::1`），
但**人還是會打 `localhost`**，而 CORS 比對的是字串不是解析結果。兩個都列，
成本是一個逗號。

（同源時瀏覽器不送 `Origin`，所以這個值多半不會被用到——但「多半」不是「不會」，
而錯的時候症狀是「某個請求被擋，沒有其他線索」。）

### D5：刪掉 `APP_API_PORT` / `APP_WEB_PORT`，不留著

移除 `ports:` 之後 `APP_API_PORT` 沒有任何使用者；`APP_WEB_PORT` 原本還被
`CORS_ORIGIN` 用，改指向代理後也沒有了。

留著的話它們會出現在 README 的「可覆寫變數」清單裡，而設了不會有任何效果——
這是本專案已經有守則在防的缺陷型態（「設定寫了但沒有執行路徑」）。刪掉。

### D6：守則放進既有的 `compose-files.spec.ts`，不開新檔

檢查的對象是 `compose.yml`，與該檔既有的三條檢查同源（執行路徑、埠號文件同步、
script 名稱）。開新檔會讓「改 compose 要看哪些守則」多一個地方要記。

守則寫成**「api 與 web 不得有 `ports:`」**，而不是「只有 nginx / postgres / redis
可以有 `ports:`」的白名單——白名單會在有人加新服務時誤報，
而那個誤報只會讓人把服務加進白名單，規則就空轉了。

## Risks / Trade-offs

- **書籤要換**：習慣 `:5173` 的人第一次會連不上，而症狀（連線被拒）
  指不到原因。緩解：README 的入口表改成一列，並明說「容器模式只有這一個」。
- **代理成為單點**：nginx 掛了整個容器環境就進不去。接受——它是官方映像
  掛一份唯讀設定檔，沒有自己的狀態；真的掛了 `docker compose restart nginx`。
- **`docker compose up -d --wait` 不保證 api 就緒**（api 沒有 healthcheck，
  `--wait` 只等到 running）。這是既有狀況，關埠沒有讓它變差，但關埠之後
  「起來了卻打不通」的第一直覺會變成怪代理。**本 change 不修**，記進 todo。
