## Why

後台的「方向感」有兩處是壞的，而兩處都不是沒人想過，是**當初的解法不夠**。

**① Sidebar 把兩個獨立的帳號體系放在同一組**：

```
使用者與權限
  會員管理     ← /members，後台管理員帳號
  前台會員     ← /front-users，聊天服務的使用者
  角色管理     ← 只作用於上面那個，前台沒有角色的概念
```

`_nav-items.ts` 與 `ui-user-management` 的 spec 都寫著「標籤不能只叫『會員』，
兩個都叫會員會讓人在錯的體系裡找人然後以為對方不存在」。加「前台」前綴是當時的解法。

**但只加前綴不夠**：`會員管理` 沒有說自己是後台的，兩個標籤都以「會員」結尾，
掃過去還是要停下來讀完才分得出來。**靠讀者仔細讀標籤的設計，遲早會被讀錯。**

**② 首頁還是模板的佔位頁**：

```tsx
管理後台骨架已建立完成，後續會接上會員、角色、權限等模組。
```

那三個模組**全部接完了**（`/members`、`/roles`、`/front-users`），
而 `/me` 那段的註解還寫著「**示範**：呼叫 /me 取登入者資料」。
於是登入後的第一個畫面，講的是一個早就不存在的狀態。

它一直沒改是有原因的（記在 `tasks/todo.md`）：**首頁對所有登入者開放，
而營運數字需要 `MODERATION:VIEW`**——不能假設看得到。那個限制成立，
但它推導出的結論應該是「內容依權限決定」，不是「留著佔位文字」。

## What Changes

- **Sidebar 分組改依「管理誰」切分**：

  | 現況 | 改成 |
  | --- | --- |
  | 使用者與權限（會員管理 / 前台會員 / 角色管理） | **管理者與權限**（管理者帳號 / 角色權限）<br>**會員管理**（會員列表） |
  | 安全 | **安全管理** |
  | 聊天管理 | 不變 |

  判準是換一個維度命名：**「管理者 / 會員」說的是「是誰」**，
  「後台 / 前台」說的是「在哪個系統」。操作者腦中的問題是前者。

- **`會員管理` 這個字串換了指涉對象**：原本是後台帳號，改成前台會員。
  **BREAKING（操作面）**：熟悉舊介面的人會撞一次肌肉記憶。
  舊用法本來就是錯的——後台帳號不是「會員」。

- **首頁拿掉佔位文字**，改成「Sidebar 給不了的東西」：營運概況與個人資料。
  **刻意不放功能捷徑**——Sidebar 常駐且不可收起，再列一次是純粹的重複。

- **有 `MODERATION:VIEW` 才顯示營運摘要**，重用既有的 `GET /moderation/dashboard`
  快照端點。沒有權限就整張卡不渲染。

## Capabilities

### Modified Capabilities

- `ui-user-management`：Sidebar 入口的群組與標籤（現行明訂「使用者與權限」群組、
  標籤「前台會員」）。
- `ui-member-management`：Sidebar 項目的標籤（現行明訂「會員管理」）。
- `platform-frontend-conventions`：Sidebar 分組的規範補上**分組的判準**
  ——現況只說「依 group 分組渲染」，沒有說 group 該怎麼切，而這次的問題正是切錯了維度。

### New Capabilities

- `ui-home`：首頁的畫面行為。目前沒有任何 spec 涵蓋它，
  所以那句佔位文字過期了兩個月也沒有東西會發現。
  三條需求：內容依權限決定、不得重複 Sidebar 的導覽、不得留下描述舊狀態的文字。

## Impact

**程式碼**：

| 檔案 | 改動 |
| --- | --- |
| `apps/web/src/routes/_nav-items.ts` | 4 個 group、2 個 label |
| `apps/web/src/routes/home/page.tsx` | 整頁重寫 |
| `apps/web/src/routes/members/page.tsx`、`front-users/page.tsx` | 標題與說明文字對齊 |

**沒有**：路由、權限碼、API、資料庫、compose 變更。**零行為變更。**

**不做**：手風琴折疊（見 design D3）；關掉 api / web 的對外埠——
那是容器環境的事且會推翻上一個 change 剛寫進 spec 的需求，另開 change。
