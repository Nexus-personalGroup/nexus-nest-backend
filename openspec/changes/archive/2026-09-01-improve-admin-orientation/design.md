## Context

兩處「方向感」問題，共同點是**當初都有人想過，但解法停在半路**：

- Sidebar 的標籤衝突有註解、有 spec 條文寫著「不能只叫會員」——加前綴是那時的解法。
- 首頁的佔位文字**刻意沒改**，理由記在 todo：「首頁對所有登入者開放，
  而營運數字需要 `MODERATION:VIEW`」。那個限制成立，但它推導出的結論
  應該是「內容依權限決定」，不是「留著佔位文字」。

## Goals / Non-Goals

**Goals:**

- 兩個帳號體系在 Sidebar 上**一眼分得出來**，不必讀完標籤。
- 首頁講「現在能做什麼」，且對任何權限組合都成立。
- 首頁只放「Sidebar 給不了的東西」，不重複導覽。

**Non-Goals:**

- **不做手風琴折疊**（見 D3）。
- **不關閉 api / web 的對外埠**——那是容器環境的事，
  且會推翻上一個 change 剛寫進 `platform-container-dev` 的需求，另開 change 才留得下紀錄。
- **不動路由、權限碼、API**。純前端文案與版面。

## Decisions

### D1：分組依「管理誰」，不依「屬於哪個系統」

候選兩組命名：

| | 群組名 | 評估 |
| --- | --- | --- |
| A | 後台管理 / 前台會員 | 系統視角。要先知道「members 屬於後台」才對得起來 |
| **B** | **管理者與權限 / 會員管理** | **人的視角**。操作者腦中的問題是「我要找的人是同事還是客人」 |

選 B。**「管理者 / 會員」直接說出是誰**，而那正是使用者當下要判斷的事。

「管理者與權限」不加「管理」二字：其他三組都是「X 管理」的偏正結構，
這組是「A 與 B」的並列，再加一個「管理」會變成「管理者與權限管理」，
「管理」出現兩次讀起來卡。

**角色權限歸在管理者那組**，因為 RBAC 只作用於後台帳號——前台使用者沒有角色的概念。
這個歸屬本身就在說明一件容易誤解的事。

### D2：`會員管理` 換指涉對象是刻意的，不是疏忽

改完之後 `會員管理` 從「後台帳號」變成「前台會員」。
**同一個詞指向相反的東西**，熟悉舊介面的人會撞一次。

接受這個代價，因為**舊用法本來就是錯的**：後台帳號不是「會員」，
那個詞從模板繼承而來，在單一帳號體系時沒問題，分表之後就錯了。
撞一次換一個長期正確的詞，划算。

替代方案是兩邊都改成全新的詞（例如「後台帳號」/「前台會員」）以避免撞車，
但那讓兩個標籤又回到「都要讀完才分得出來」——**而那正是這次要修的問題**。

### D3：不做手風琴折疊

現況 9 個項目、4 組，畫面下半部是空的。折疊在這個規模是：
多一次點擊、**收起來的組變得難以發現**、多一份狀態要管（哪組開著、換頁記不記得）。

它解決的是「項目多到放不下」，而現在的問題是「兩個標籤長太像」——**分組就能解決**。
等前台那組長到三四個項目、整體超過 15 個再回來考慮。

### D4：首頁不放功能捷徑

原本設計了一張「快速入口」卡（由 `NAV_ITEMS` 衍生，避免手寫第二份清單）。
**實作完看到畫面後拿掉了**——Sidebar 是常駐且不可收起的，
在首頁再列一次同樣的連結是純粹的重複，佔掉使用者第一眼的注意力
而沒有提供任何 Sidebar 給不了的東西。

連帶收回了為此抽出的 `filterNavItems`：那個抽象唯一的目的是給首頁共用，
**沒有第二個呼叫端就不該存在**。`_layout.tsx` 回到原本的內嵌寫法。

spec 保留「若日後真的加了捷徑，必須由 `NAV_ITEMS` 衍生」作為條件式的規則
——那個判斷仍然成立，只是現在沒有觸發它的東西。

首頁因此只剩「Sidebar 給不了的」：營運概況（需權限）與個人資料。
對沒有任何 VIEW 權限的人來說那就只有個人資料——**那是誠實的**，
比一張重複的捷徑卡好。

### D4b：首頁的數字是快照，時間戳用絕對時間

首頁用 `GET /moderation/dashboard` 的一次性快照，**不輪詢也不訂閱 SSE**。
盯即時數字是完整營運總覽的職責；在首頁加輪詢等於把那頁的職責搬過來，
而代價是每個登入者的首頁都多一份固定成本。

**因此時間戳必須是絕對時間。** 第一版用了 `formatRelativeTime`（「剛剛」），
但那對不會更新的數字是錯的——頁面開著不動，「剛剛」會一直是「剛剛」。

**而且要含日期。** 只有「14:32」在跨日之後會被當成今天的，
那正是總覽頁註解警告的那件事：「一個安靜地顯示 20 分鐘前數字的儀表板
比沒有儀表板更糟——它讓人以為自己知道現況」。

### D5：資訊揭露用「隱藏」，動作用「disabled」

首頁的營運摘要在無權限時**整塊不渲染**，而不是顯示「無權限」或空數字。

這沿用 `ui-moderation` 已經定下的判準，但方向相反的那一半也要記住：
**動作**在無權限時 disabled 並說明理由（使用者需要知道「這件事做得到，
只是不是由我做」），**導覽與資訊揭露**則直接隱藏（看得到但點不進去更令人困惑）。

### D6：新開 `ui-home` capability

首頁目前**沒有任何 spec 涵蓋**——那正是佔位文字能過期兩個月的原因：
沒有東西描述它應該是什麼，也就沒有東西會發現它不是。

新增的三條需求裡有一條刻意是「不得留下描述舊狀態的文字」。
那條看起來瑣碎，但它是唯一能擋住同類問題復發的東西。

## Risks / Trade-offs

- **[`會員管理` 換了意思，操作者會撞一次]** → D2 評估過，接受。
- **[首頁多打一支 API]** → 只有具 `MODERATION:VIEW` 的人會觸發，
  且重用既有的快照端點（不是新端點）。無權限者的首頁請求數不變。
- **[~~快速入口與 Sidebar 顯示同一批東西，可能顯得重複~~]** → **這個風險成真了**，
  實作完看畫面就確認了重複。已拿掉整張卡（見 D4）。
  記在這裡是因為它示範了一件事：**版面的重複只有看到畫面才判斷得出來**，
  寫 design 時列為「風險」的東西，實作後要回頭確認它有沒有發生。

## Migration Plan

無 schema、無 migration、無環境變數。純前端，部署即生效。

回滾：兩塊各自獨立，任一塊可單獨 revert。
