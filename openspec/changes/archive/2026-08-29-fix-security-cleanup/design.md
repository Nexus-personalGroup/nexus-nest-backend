## Context

2026-08-22 審查報告的 🔴 已由 change 1、2、6 修完，剩五項 🟡🟢。
開工前逐項確認過**現在仍未修**，位置與症狀與報告一致。

五項的共同性質：都在「還沒出事，但出事時會放大」的位置，
而且**都不會有徵兆告訴你它壞了**——CSP 全關不會報錯、
fail-open 不會留痕跡、心跳堆疊只是讓人「看起來離線」、
文件裡的過期數字看起來跟正確數字一模一樣。

## Goals / Non-Goals

**Goals:**

- CSP 的豁免範圍跟著它的理由走：只有 API 文件路徑。
- refresh token 的效期與其儲存方式相稱。
- 安全防護的降級留下痕跡（日誌 + 指標）。
- 心跳不重入、不逐條往返。
- 文件漂移修掉，其中守則數量那條**用守則自己釘住**。

**Non-Goals:**

- **不做 refresh token 的 cookie 化**（見 D2）。
- **不推翻 fail-open 的選擇**（見 D3）——只讓它可觀測。
- **不動 `WS_HEARTBEAT_INTERVAL` 與 presence TTL 的數值**（見 D4）。
- **不處理審查報告的問題 10（WS 連線數 TOCTOU）**——超額一兩條無實質危害，
  且修法要在寫入後回讀再回收，複雜度不成比例。留在 todo。

## Decisions

### D1：以單一分支中介層切換兩份 helmet 設定

Express 的 `app.use(path, mw)` 只是「前綴符合才跑」，**不會讓後面的 `app.use(helmet())` 跳過**
——文件路徑會被兩份設定先後套用，第二份把 CSP 加回去。

因此用一個明確的分支：

```
app.use((req, res, next) =>
  isDocsPath(req.path) ? helmetForDocs(req, res, next) : helmetDefault(req, res, next));
```

兩個 helmet 實例在模組載入時各建一次。判斷寫成具名函式而非行內字串比對，
因為文件路徑有兩條（admin / front），而**漏掉其中一條的症狀是「那份文件打不開」**
——會被當成 Swagger 壞掉去查，不會有人想到是 CSP。

**不用 `NODE_ENV` 決定**：開發與正式跑不同的 CSP，等於把違規延到正式環境才發現。

### D2：效期壓到 1 天，cookie 化留待日後

三個候選：

| 做法 | 評估 |
| --- | --- |
| **效期 7 天 → 1 天** | 一行改動，把爆炸半徑從 7 天縮到 1 天 |
| 改 `httpOnly` + `SameSite=Strict` cookie | **真正的修法**——XSS 讀不到。但要動登入 / 換發 / 登出三條路徑、前端的 token 存取層、CORS 的 credentials 設定與 e2e |
| 維持現狀，靠 CSP 擋 XSS | CSP 是縱深防禦不是保證；且**這正是本 change 要修的那個 CSP** |

選第一個，第二個列 Non-Goal。理由是**這次要收的是「低成本高效益」的尾巴**，
cookie 化的成本量級與其他四項不同，混進來會讓整個 change 卡在它身上。

但 spec 寫的是「效期與儲存方式**這一組**」而不是「效期是 86400」——
日後真的改成 cookie 時，重新評估效期是被允許的，不必再回來改規則。

### D3：留痕跡，不改變放行行為

fail-open 是刻意的：Redis 掛掉時若連登入都擋，等於把快取故障升級成全站故障。
**本 change 不推翻這個選擇**，只補上它缺的那一半——現在完全沒有痕跡。

方向不一致本身是可辯護的（認證 fail-closed、防護 fail-open），
真正的問題是**沉默的那一邊風險更高**：503 會有人立刻發現，靜默放行不會。

指標與日誌都要：指標用於「上週那波嘗試發生在防護有效還是失效時」，
日誌用於當下排查。**兩者不可只做其一**——指標沒有上下文，日誌不能聚合。

### D4：批次心跳走 port，不讓 gateway 碰 Redis

`sendHeartbeats()` 在 `adapter/in/ws`，續期經 `PresencePort`。
批次化不能讓 gateway 直接拿 Redis client——那會穿透分層。
作法是 port 上新增 `heartbeatMany(entries)`，adapter 內用 pipeline 把
N 組 `hSet + expire` 合成一次往返。

**防重入與批次是兩件事，都要做**：批次讓單輪變快，但**變快不等於不會超時**
（Redis 延遲抬高時照樣會）。旗標是那個保證的來源，批次只是讓它更少被觸發。

跳過一輪是安全的：presence TTL 涵蓋數個心跳週期。
**不用「排隊等下一輪」**——排隊就是堆疊的另一種寫法。

**不調整 `WS_HEARTBEAT_INTERVAL` 與 TTL**：那兩個數字現在的比例（15s / 60s）
是合理的，問題出在單輪耗時而不是週期設定。改數字是用調參掩蓋機制缺陷。

### D5：守則基準值只擋「變少」

自我斷言若要求精確相等，每加一條守則就要改一次期望值——
那種規則會被當成雜訊繞過，最後跟寫死在文件裡的數字一樣沒用。

因此只斷言「不低於基準」。基準值放在守則檔自己裡面，
新增守則時不必動它；累積一段時間後再往上調（調整本身是刻意的動作，不是維護負擔）。

**文件不再寫數量**：`CLAUDE.md` 改成不帶數字的描述。
數字只在 `test:arch` 的輸出裡，那是唯一不會過期的地方。

### D6：五項綁一個 change，但切成獨立可驗證的塊

1 與 2 是同一個放大器的兩端（CSP × localStorage × 效期），拆開看都「還好」，
合在一起才是完整的論述——**它們屬於同一個 change**。
3、4、5 各自獨立，但規模都小到不值得各開一個 change 的流程成本。

塊之間沒有相依，每塊自己驗證、自己綠。

## Risks / Trade-offs

- **[CSP 上線後後台 SPA 可能有資源被擋]** → 這正是要修的東西暴露出來的實際情況。
  e2e 驗 header 存在，但**「頁面還能不能用」只有人工驗得到**——
  smoke-test 必須包含實際打開後台走一輪。
- **[效期改 1 天讓所有人隔天要重新登入]** → 刻意的。後台管理系統每天登入一次
  不算苛刻，而這是把爆炸半徑從 7 天縮到 1 天的代價。
- **[Redis 掛掉期間每次登入失敗都寫一則 warn，可能刷版]** → 接受。
  Redis 掛掉時日誌本來就會吵，而**這則警告正是那段期間最該被看到的東西**。
  若日後真的造成困擾，該做的是聚合而不是降級成 debug。
- **[批次心跳讓單輪的失敗變成整批的失敗]** → pipeline 內單一命令失敗不影響其他命令，
  但要驗：spec 明訂「某條失敗時其餘 MUST 仍完成」。
- **[守則基準值長期不調就失去意義]** → 只擋變少本來就是刻意放寬。
  它防的是誤刪，不是「守則有沒有持續增加」。

## Migration Plan

無 schema 變動、無資料遷移。

**需要使用者手動處理一項**：`REFRESH_TOKEN_EXPIRES_IN` 若已在 `.env` 顯式設過，
改預設值不影響該環境——要一併調整 `.env` 才會生效。
`.env.example` 由本 change 更新。

回滾：五塊各自獨立，任一塊可單獨 revert。
CSP 那塊若上線後發現後台有資源被擋，最快的止血是把該資源加進 directives，
而不是改回全域關閉。
