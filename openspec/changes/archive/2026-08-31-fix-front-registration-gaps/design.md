## Context

2026-08-30 審查報告的問題 1～5，五項逐項驗證屬實，全部落在前台註冊流程（3b）。

**五項有同一個形狀**：正確答案早就在這個 codebase 裡了，只是沒走完最後一步。
`API_BASE_URL` 定義好放著零使用、IP 封鎖的防線寫在註解裡但沒接上、
P2002 在其他四張表都接了只有最新那張漏掉、
「能收到信就證明他擁有信箱」已經白紙黑字寫在忘記密碼的註解裡。

這不是判斷失誤的集合，是**新區域沒有繼承既有模式**。

## Goals / Non-Goals

**Goals:**

- 驗證信的連結指向後端，並由**直接斷言字串**的測試守住。
- 前台 auth 的每一支端點都有自己的節流。
- `FrontLoginService` 註解描述的 IP 防線真的存在。
- 併發註冊同一信箱回 409 而非 500。
- 重設密碼一併標記信箱已驗證。

**Non-Goals:**

- **不做 reCAPTCHA**（見 D4）。
- **不做「對外 URL 都要有斷言」的守則**（見 D2）。
- **不動 `users` 的搜尋索引**（報告問題 6）——還沒到會痛的規模，報告自己也說先別動。
- **不做群組邀請的同意權**（報告問題 8）——那是產品決策，該進路線圖不是進這個 change。
- **不動 module 歸屬**：`RevokeMemberSessionsService` 住在 `chat-ws.module` 的問題
  留在 todo，本 change 的塊 4 只加注入、不改任何模組的歸屬。

## Decisions

### D1：連結的 base 用 `API_BASE_URL`，並讓它成為 production 必填

`API_BASE_URL` 定義在 `validate-env.ts:11`，**全 codebase 零使用**。
它不是遺留垃圾——它正好是這裡缺的那一塊。

**它現在是 `z.string().optional()`，型別是 `string | undefined`**，
所以「改一行」實際上是兩步：先給預設值（`http://localhost:3000`）
並列入 `productionErrors`，才能 `.replace()`。順序不能顛倒，否則不過 typecheck。

列入 `productionErrors` 的理由與 `APP_FRONT_URL` **一模一樣**：
少了它連結就壞，而且**壞得無聲**——信寄出去了、狀態碼是對的，
只有點下去的人看到 404，而他沒有管道回報。

替代方案是「從請求推導 origin」（`req.protocol + req.host`）：**不採用**。
寄信發生在 service 層而非請求脈絡裡，硬要傳進去等於讓 domain 相依 HTTP；
而且反向代理之後那個值本來就不可信。

### D2：不做「對外 URL 都要有斷言」的守則，改用三行測試

報告的結論建議加一條守則：「凡是由 env 組成的對外 URL 都要有斷言」。**不做。**

守則沒有辦法知道一個字串是「對外」還是「對內」——寫出來會是一組正則猜測
（比對 `${env.` 加上 `URL` 之類），而它擋不住同一類問題的下一個變形，
卻會在每次有人組任何字串時發出假警報。**一條會誤報的守則會被繞過，
繞過之後它連原本那點價值都沒有了。**

真正的修法是**直接斷言那個字串**，三行就夠，而且精準度是 100%。

唯一划算的守則版本是型別層面的那個：`API_BASE_URL` 必須有預設值
——那由 zod schema 自己保證，不需要額外寫規則。

**但要記下這個測試缺口的形狀**：「送到系統外面去的字串」
（信件連結、302 導回目標、日後的 webhook URL、推播 deep link）
的共同特徵是**在系統內部永遠不會被呼叫**，所以任何「呼叫自己」的測試都驗不到。
這一句要進 `openspec/project/testing.md`，那比守則有用。

### D3：節流用端點層 `@Throttle`，不自己造限流

專案已經有全域 `ThrottlerGuard`，後台的 `forgot-password` / `reset-password`
已經在用 `@Throttle({ default: { limit: 3, ttl: 60_000 } })`。前台沿用同一個機制。

額度：**登入 5／分鐘、寄信類 3／分鐘**（與後台同類端點對齊），
其餘（refresh / logout / verify-email）**同樣要宣告**，給較寬的 10／分鐘。

**八支全部宣告，不做「哪幾支需要」的判斷。** 一開始想讓 refresh / logout
沿用全域（它們要帶 token 才走得到），但那是一個**會被答錯的判斷**——
下一個加端點的人得先想清楚它算不算敏感，而想錯不會有任何徵兆。
「每一支都宣告」沒有判斷空間，也才守得住（spec 的 scenario 直接檢查有沒有宣告）。

**不自己寫 per-IP 計數器**：`IpBlockPort` 那條是**累積式的封鎖**
（達門檻進黑名單），與節流是不同的東西，兩者都要但不能互相取代。
節流擋的是速率，黑名單擋的是持續攻擊。

### D4：reCAPTCHA 另開

port 與 adapter 都已存在（後台登入在用），接上去技術上不難。
不放進來的理由是**它需要前台配合**——前台要嵌 widget、要處理 token，
而前台是還沒開始的獨立 repo。現在接上去等於讓前台第一天就得處理一個
沒有人驗證過的整合。等前台開工時一起做，那時能真的端到端驗一次。

### D5：P2002 照抄既有寫法，並把「先查」的角色寫清楚

`PrismaMemberRepository` 三處、`ChatRoom`、`ChatMessage`、`ChatReport` 四張表
都已經把「唯一索引衝突是正常結果而非錯誤」寫進註解。照抄。

值得在註解裡寫清楚的是**「先查」的角色變了**：
它不再是「防止衝突」（那是唯一索引的工作），而是
「給出更好的錯誤訊息，並在未驗證的情況下順便重發驗證信」。
少了這句話，下一個人會以為先查是多餘的然後把它刪掉，
而那會讓「已註冊但未驗證 → 重發驗證信」這條路徑消失。

### D6：重設密碼標記已驗證，選「一併標記」而非「前台提示」

兩條路：(1) 重設成功時一併 `markEmailVerified`；(2) 導回時帶「尚未驗證」狀態，
讓前台提示他去驗證。

選 (1)。判準是**憑證的強度**：重設信與驗證信送到同一個信箱、
用同一組 sha256 雜湊儲存的一次性 token、同一套 `invalidateOthers` 作廢邏輯。
「能收到就證明他擁有它」這句話對兩者同樣成立——而那句話本來就寫在
`FrontForgotPasswordService` 的註解裡，只是沒走完最後一步。

(2) 的問題是它把一個已經被證明的事實丟掉，然後要求使用者再證明一次，
而他要去點的那封信**可能就是當初沒收到才走到忘記密碼的**。

`markEmailVerified` 已是條件式更新（`where` 帶 `emailVerifiedAt: null`），
所以已驗證的帳號重設密碼不會覆寫原本的驗證時間。

## Risks / Trade-offs

- **[`API_BASE_URL` 成為 production 必填，既有部署會啟動失敗]** → 刻意的，
  與 `APP_FRONT_URL` 同一個判準。啟動失敗是可見的，連結壞掉不是。
  部署前要設，這一條會寫進收尾的「需要使用者手動執行」。
- **[登入節流 5／分鐘可能誤傷共用出口 IP 的使用者]** → 前台尚未上線，
  沒有實際流量可以校準。5 是與後台同類端點對齊的保守值，
  上線後若誤傷再依實際數據放寬——**先緊後鬆**比反過來安全。
- **[重設密碼標記已驗證，多了一條會改 `emailVerifiedAt` 的路徑]** → 這正是 D6
  評估過的疑慮。結論是那條路徑的憑證要求不比驗證信弱，因此可接受。
- **[IP 失敗計數接上前台後，兩側共用同一組計數器]** → `buildFailedIpKey` 以 IP 為鍵、
  不分側，因此後台與前台的失敗會累加。**這是對的**——同一個 IP 在兩側輪流試密碼
  仍然是同一個攻擊者。要記在註解裡，否則下一個人會以為是 bug。
