## Context

`add-chat-messaging` 建了「WS 事件必須表態限流」的守則，但那條規則只要求
**逐個 use case** 表態。當時就寫下了它的不足：

> 針對讀取濫用的正確防線是「連線層的事件限流」而非逐個 use case 接——
> 只擋這一支會給出覆蓋完整的錯覺，而 `ping` / `joinRoom` 仍然不受限。

這個 change 補上那條防線。範圍是使用者選定的：**超過時回錯但不斷線**。

## Decisions

### D1：計數放本實例的記憶體，不走 Redis

送訊息的限流用 Redis（`throttleIncrement`），因為那是**業務規則**：
「這個人在這個房間發太多訊息」與他連幾條線、連到哪個實例無關。

連線層的限流不同——它保護的是**這個行程的事件迴圈**。
一條連線只存在於一個實例上，計數也只有那個實例需要。

走 Redis 會有三個代價，而且都沒有對應的收益：

- **每個事件多一次網路往返**：限流本身變成它要防的那種負載
- **Redis 成為每個 WS 事件的單點**：它掛掉時要嘛全部放行（防護消失）、
  要嘛全部擋下（聊天整個停擺），兩個都比「本機計數」差
- **跨實例的一致性沒有意義**：同一條連線不會同時出現在兩個實例上

**代價要認**：一個惡意使用者開 N 條連線就有 N 倍的額度。
但那是「連線數」的問題，而它已經有 `WS_MAX_CONNECTIONS_PER_MEMBER` 管著。
兩條防線各司其職，不要互相取代。

### D2：超過時回錯但不斷線

丟棄該事件、回 `server:error`（`code: WS_RATE_LIMITED`），連線維持。

**為什麼不斷線**：誤判的代價不對稱。網路拖慢造成的瞬間爆量、
或客戶端的重試邏輯，都可能短暫超過門檻——把人踢下線會讓一個
**暫時性的異常變成使用者可見的故障**，而客戶端還會自動重連造成更多負載。

回錯則讓客戶端有機會自己退避，而且行為與既有的送訊息限流一致
（同一個系統裡兩種限流用兩種處置會讓客戶端難以實作）。

**這條防線的目標不是擋住蓄意攻擊者**——他可以開更多連線。
它的目標是**讓失控的客戶端無法拖垮實例**，而回錯就足以達成。

### D3：套用到所有事件，包含 `ping`

`ping` 看起來無害（只回一個字串），但**「無害」是就單次而言**。
每秒一萬個 ping 一樣會佔滿事件迴圈——而連線層限流要防的正是這個。

不做例外清單：例外會逐漸長大，而**每多一個例外就多一條不受限的路徑**。
心跳的正常頻率是每 15 秒一次，離任何合理的門檻都很遠。

### D4：閾值設在遠高於合理客戶端的水準

預設每秒 20 個事件。正常的聊天客戶端穩態下遠低於這個數字
（心跳 15 秒一次、送訊息受打字速度限制）。

**這個門檻不是用來精細控制的**，它是「明顯失控」的界線。
設太低會誤傷合理的批次操作（例如重連後連續 join 多個房間），
而那類誤傷會以「偶爾有房間加不進去」的形式出現——很難查。

### D5：與逐 use case 限流並存，不取代

送訊息仍然保留自己的限流（每人每房間），因為兩者問的問題不同：

| | 連線層 | 送訊息 |
| --- | --- | --- |
| 保護什麼 | 這個行程的事件迴圈 | 房間不被洗版 |
| 計數單位 | 單一連線 | 成員 + 房間（跨連線、跨實例） |
| 開 N 條連線 | 額度 × N | 額度不變 |

**連線層限流無法取代送訊息限流**：開 10 條連線就能繞過前者，但後者不受影響。
守則要明說這件事，否則日後有人會以為「已經有連線層限流了」而移除業務層的。

## Open Questions

- **要不要為不同事件設不同權重**（例如 `syncRoom` 比 `ping` 貴）：
  現在一律算一個事件。等有實際的負載資料再說——現在猜權重會猜錯。
- **要不要出成指標**：`chat_ws_throttled_total` 是合理的，
  但先看看它實際上會不會觸發。零觸發的指標只是雜訊。

## 為什麼現在不做「連續超過就斷線」

使用者選了「回錯不斷線」。若日後要升級成兩階段（超過先回錯、
反覆超過才斷線），需要的是**違規次數的狀態與它的過期策略**——
那實際上是第二套限流疊在第一套上面。

現在的實作不擋住那條路：計數器已經在連線物件上，加一個「違規次數」
是同一個位置的事。但**不預先加**，那是替一個還沒決定的行為猜規格。
