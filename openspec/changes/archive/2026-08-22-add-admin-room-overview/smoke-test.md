# add-admin-room-overview 手動驗證

前置：`pnpm dev`，用有 `BACKEND:MODERATION:VIEW` 的帳號登入後台，
系統中至少要有一個群組、一個私聊、一筆檢舉。

## 1. ⭐ 走完一整條動線

**這是這個 change 的核心，也是 CI 驗不到的部分。**

從 Sidebar 的「檢舉審閱」開始，一路點下去，中途**不要用返回鍵、不要回任何列表**：

1. 檢舉佇列 → 點一筆的「檢視」
2. 檢舉詳情 → 點「被檢舉人」
3. 成員概覽 → 在「所在聊天室」點一個房間
4. 房間詳情 → 在成員清單點另一個人
5. 又回到成員概覽（不同的人）

五步都能點得動才算接起來。**任何一步點不動，動線就是斷的**——
而斷掉的那一步會讓審閱者退回列表重新搜尋。

## 2. ⭐ 房間詳情沒有任何通往訊息的入口

**這一項只有人工看得出來。**

在房間詳情頁上下捲一遍，確認**沒有**任何「查看訊息」「訊息紀錄」之類的按鈕或連結。

這是刻意的界線：看得到房間訊息是實質擴權——從「有人檢舉，你才看得到被檢舉的那一句」
變成「你能瀏覽任何房間的完整對話」。前者的每一次查看都有外部觸發的理由，後者沒有。
要看內容仍然只能經由檢舉。

## 3. 訊息量的語意

進 `/moderation/rooms`，把滑鼠移到「訊息量」欄位標題旁的 ⓘ 圖示，
確認提示寫著「歷史累計，含已撤回與已被移除的訊息」。

實測一次：找一個房間記下數字 → 從檢舉詳情移除該房間的一則訊息 → 回列表，
**數字不變**。它算的是「曾經有多少則」，不是「現在顯示中的則數」。

不標明的話這個數字會被讀成後者，而兩者在有人撤回過訊息之後就不一樣了。

## 4. 類型篩選與私聊的名稱

切換「全部 / 群組 / 私聊」，確認：

- 篩選結果正確，且 `roomType` 進了網址、重新整理後保持
- **私聊那一列顯示「私聊」而不是空白**——私聊沒有名稱（顯示名由對方決定，不落庫）

## 5. 帳號已刪除的成員仍在房間裡

把某個房間成員軟刪除：

```sql
UPDATE members SET deleted_at = NOW() WHERE id = '<成員 id>';
```

回房間詳情，確認：

- 該位顯示「已刪除的帳號（尾 8 碼）」而不是消失
- **成員數與清單長度仍然一致**——把他拿掉會讓兩個數字對不起來，
  而那種不一致看起來像 bug、查起來卻查不到原因
- 他仍然可以點（概覽頁會回 404 並說明）

**不要刪自己正在使用的帳號**——token 會失效，症狀是整頁 401 而錯誤訊息指不到原因。
驗完記得改回 `deleted_at = NULL`。

## 6. 權限

用只有 `BACKEND:ACCOUNT:VIEW`（沒有 MODERATION）的帳號登入：

- Sidebar 看不到「聊天室」
- 直接打 `/moderation/rooms` 會被導回首頁，且 Network 上**沒有**任何請求發出去
