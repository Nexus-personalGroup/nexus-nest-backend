## Context

後台唯一還沒有列表的實體是聊天室。前兩個 change 把「檢舉 → 人」與「人 → 房間清單」
接了起來，但房間本身點不進去——動線在這裡斷掉。

範圍由使用者定下：**只讀、不看訊息**。這兩個限制讓這個 change 不碰內容存取，
也不新增任何處置概念。

## Decisions

### D1：訊息量直接用 `chat_rooms.last_seq`，不 count

`last_seq` 是房間內已配出的最大序號，而**訊息列永遠不會被刪除**
（刪掉會讓 `seq` 出現洞，補齊的客戶端無法區分「被清掉」與「我漏收了」——
那是訊息撤回堅持軟刪除的同一個理由）。

因此 `last_seq` **就是**這個房間的歷史訊息總數，零查詢成本：它已經在房間那一列上。

`count(*)` 反而會給出**不同且更差**的數字：它算的是「目前還在的列」，
而在「訊息永不刪除」的前提下兩者本來就相等——多花一次查詢換一個相同的答案。
若日後真的做了訊息清理，`count` 會開始少算，而 `last_seq` 仍然誠實地
回答「這個房間曾經有多少訊息」——那才是營運要看的數字。

**要標明它的語意是「歷史累計」而非「目前存在」**，否則日後有人會拿它跟
資料庫的實際列數對不起來而以為有 bug。

**沒有任何測試分得出 `last_seq` 與 `count(*)`**（反向驗證確認過：換成 count 仍全綠），
因為在「訊息永不刪除」的前提下兩者相等。測試守得住的是**語意**——
把 count 加上 `where: { removedAt: null }` 就會紅。資料來源的差別要等真的做了
訊息清理才顯現，所以這個選擇靠的是這段文字而不是守則。

### D2：成員清單帶 email，沿用既有的批次補值

房間的成員關係只存 `memberId`（不建外鍵——帳號刪除的處置屬於業務決定）。
與檢舉當事人同樣的問題、同樣的解法：service 層一次批次查
`LoadMemberPort.findEmailsByIds()`，查不到就是 `null`，前端顯示「已刪除的帳號」。

這是第三次用同一套做法。**不要為此抽出共用的「補 email」helper**——
三處的輸入形狀都不同（檢舉是兩造、成員概覽是對造、房間是成員陣列），
共用的抽象會需要一個 selector 參數，而那比重複三行 `map` 更難讀。

### D3：詳情頁的成員清單不分頁

房間成員數受業務常識約束（群組上限不是無限），而分頁一個 20 人的清單
只會多一組狀態要管。**若日後出現大型群組**（數百人），這裡要改成分頁——
判斷點是「一次回傳的成員數會不會讓回應變大到有感」。

私聊固定兩人，這個決定對它完全無影響。

### D4：房間列表的排序成本，現在不加索引

預設依 `createdAt` 遞減排序，而 `chat_rooms` **沒有 `createdAt` 索引**——
Postgres 會全表排序後取前 N 筆。

**現在不加**，理由與「不為訊息則數加 `senderId` 索引」一致但強度不同：
房間數比訊息數少好幾個數量級（每個房間承載大量訊息），
排序幾千列是次毫秒等級的操作。加索引要付的是每次建房間的寫入成本，
而收益在目前的資料量下量測不出來。

**要記下判斷點**：房間數到達數十萬時這個查詢會開始有感，那時加
`@@index([createdAt])` 是單純的 migration，不需要改任何程式碼。
寫在這裡是為了讓那一天有人查得到「當初為什麼沒加」。

### D5：三個實體互相連得起來才叫動線

檢舉詳情 → 成員概覽（已完成）、成員概覽 → 房間詳情（本 change）、
房間詳情 → 成員概覽（本 change）。

單獨看每一條連結都只是「順手加個 `<Link>`」，但少了任何一條，
審閱者就會在某個點卡住而必須回頭重新搜尋。**動線的價值在完整，不在每一段**。

房間詳情**不連往訊息**——那條路不存在，而它的不存在是刻意的。

### D6：類型篩選只有兩個值，不做「全部」以外的複雜條件

`roomType` 篩選提供「全部 / 群組 / 私聊」。不做名稱搜尋——
群組名稱不是唯一的、私聊根本沒有名稱，一個搜尋框在半數資料上不會有結果，
那種功能比沒有更容易誤導。

要找特定房間的路徑是「從人或從檢舉點進去」，那也是實際的動線。

## Open Questions

- **要不要顯示「最後一則訊息的時間」**：那是判斷房間死活最直接的訊號，
  比訊息總量有用。但 `chat_messages` 沒有適合的索引可以便宜地取到它
  （`(roomId, seq)` 可以取最大 seq 那一列，其實不貴）——
  等實際用過列表之後再看是不是真的需要，現在加會讓每一列多一次查詢。
- **私聊要不要顯示「兩個人是誰」**：列表上的私聊目前只會顯示「私聊」，
  分不出是誰跟誰。要顯示得對每一列查成員，那是 N+1。
  詳情頁看得到，先接受列表上的模糊。

## 為什麼不看訊息

使用者選了「不看訊息」，而這個選擇值得記下理由，因為日後一定有人會提議加。

看得到房間訊息是**實質擴權**：從「有人檢舉，你才看得到被檢舉的那一句」
變成「你能瀏覽任何房間的完整對話」。前者的每一次查看都有一個外部觸發的理由
（有人按了檢舉），後者沒有。

技術上的代價只是次要的：新的內容存取路徑要在
`chat-message-single-entry.spec.ts` 開豁免、要寫稽核、要決定被撤回與已移除的
內容如何呈現。但真正的問題是**「看內容必須有理由」這件事會消失**，
而它消失之後沒有任何測試會變紅。
