## Context

路線圖第 4 項，也是這一系列裡**動到最多既有程式碼**的一個。
前面每個 change 都是「加東西」，這一個是「把既有的東西整批換掉」。

3a 已經把 `users` 與前台認證建好並刻意不切換。現在切。

## Decisions

### D1：既有的聊天資料清空，不遷移

那些 `sender_id` / `member_id` 現在存的是 `members` 的 id。三種處置：

| 做法 | 評估 |
| --- | --- |
| **清空聊天資料** | 前台還沒開，現存的全是測試資料。乾淨、零風險 |
| 把 member 複製一份到 users | 保住了不需要保住的東西，代價是「同一個人在兩張表各有一個帳號」的怪狀態 |
| 寫對照表逐筆更新 | 最完整，也最沒必要——它為了 1 已經解決的問題付出最高成本 |

選第一個。**但這是破壞性動作，必須由使用者明確確認才執行**——
「我認為那些資料不重要」和「那些資料確實不重要」是兩件事。

清除範圍要包含 **Redis 的 presence 紀錄**：key 的格式不變但語意變了，
留著會讓「在線的人」指向已經不存在的身分。

### D2：停權拆成兩支，而不是加一個參數

審閱側要停的是**前台使用者**，帳號管理側要停的是**後台帳號**。
現在兩者都走 `UPDATE_MEMBER_USE_CASE`。

**不用「加一個 side 參數」的做法**：那會讓一支 use case 同時知道兩張表、
兩種撤銷連線的方式、兩種稽核對象，而每個呼叫端都要記得傳對參數——
傳錯的後果是停錯人，而那不會有任何錯誤訊息。

拆成兩支之後，「停權」這個動作的對象由**你呼叫哪一支**決定，
而不是由參數決定。型別上就不可能停錯。

連帶要拆的是**撤銷連線**：`RevokeMemberSessionsUseCase` 目前對
`personalRoom(memberId)` 廣播並斷線。前台使用者的連線在同一個 WS namespace，
但身分來源不同——邏輯相同、對象不同，因此也是兩支。

#### 實作時的修正：撤銷連線**不拆**

D2 原本要求連撤銷連線也拆成兩支。實作時發現那是把 D2 的理由推過了頭：

`RevokeMemberSessionsService` 只做兩件事——對 `personalRoom(id)` 廣播
`server:sessionRevoked`，然後 `disconnectMember(id)`。它**不查任何帳號表**，
兩側的實作會逐字相同。而 D2 真正防的是「一支 use case 同時知道兩張表」，
這裡沒有那個問題：它一張表都不知道。

改為把它的 provider 從 `admin/member.module` 移到 `ChatWsModule` 並 export，
理由與 `SEND_MESSAGE_USE_CASE` 放在那裡一樣——**它是傳輸層的操作**。
兩個停權入口因此拿到同一份實作，而不是兩份會各自漂移的複製品。

「拿管理員的 ID 呼叫它」是無害的無操作（後台帳號沒有 WS 連線）。
帳號管理側仍然照呼叫：那是「後台帳號沒有連線」這個事實的結果，
不是這一層可以假設的前提。

### D3：presence key 的格式不變

現在是 `presence:member:<id>`。改成 `presence:user:<id>` 會更精確，
但那要同時改 sweep 的 scan pattern、剛加的在線索引、以及所有相關測試——
換來的只是命名更好看。

**不改，但在 `cache-keys.ts` 的註解寫明「這裡的 member 指的是前台使用者」**。
命名的債留著，因為還債的成本大於它造成的困惑。
若日後 presence 也要涵蓋後台（例如「哪些管理員在線」），那時再改，
而那時改是有實質理由的。

### D4：前台 controller 全部掛 `FrontJwtAuthGuard`，不用路徑前綴判斷

3a 的 `FrontJwtAuthGuard` 用 `@UseGuards()` 掛在 controller 上。
本 change 把三支聊天 controller 也掛上。

**不改成「全域 guard 依路徑前綴分派」**：那看起來更省事（一處改動涵蓋所有
`/api/front/*`），但它讓「這支端點吃哪一側的 token」變成一個要去讀 guard 內部
才知道的事。掛在 controller 上是**看得見的**——打開檔案就知道。

`side-isolation.spec.ts` 已經在守著原始碼層的側別隔離；
再加一條守則要求「`front/` 下的受保護 controller 必須掛 `FrontJwtAuthGuard`」，
讓漏掛變成紅燈而不是一個吃錯 token 的端點。

### D5：審閱看到的「成員」全部是前台使用者，但**稽核的執行者仍是管理員**

要小心區分兩種 id：

- `chat_audit_logs.member_id`：**做這件事的人**。撤回訊息是前台使用者，
  但「查看檢舉」「移除訊息」「停權」是**管理員**——這一欄兩種都有
- `chat_audit_logs.target_member_id`：**被做的人**，一律是前台使用者

因此時間軸查詢（`GET /moderation/members/:id/timeline`）的語意在切換後仍然正確：
它查的是「這個前台使用者做過什麼」，而管理員對他做的事會出現在
`target_member_id` 那一側。

**這一點在補 email 時特別容易錯**：稽核紀錄的 `member_id` 若是管理員，
拿去 `users` 查會查不到。目前時間軸不顯示執行者的 email，所以沒有這個問題——
**但日後要顯示時必須先解決「這個 id 屬於哪張表」**。寫進 spec 免得踩到。

### D6：測試改用 `seedUser` + 前台 token，這是工作量的主體

所有聊天相關的 e2e 與整合測試目前都用 `seedMember` 建帳號、用 admin token 連線。
切換後它們全部要改。

**不要用「同時支援兩種」的過渡寫法**——那會讓測試看起來仍然通過，
卻不再驗證真正的路徑。改就一次改完。

## Open Questions

- **後台管理員要不要也能用聊天**（例如客服直接與使用者對話）：
  目前不行，而且本 change 讓它在型別層面不可能。若日後要做，
  正確的形狀是「客服身分」而不是「讓管理員的 id 進聊天」。
- **`chat_audit_logs.member_id` 要不要加一欄標示執行者的側別**：
  現在靠上下文（動作類型）就能推斷，加欄位是為了日後顯示執行者。
  等真的要顯示時再加。

## 為什麼不順便做後台的前台使用者管理

那是路線圖第 5 項。本 change 已經動到 11 支 service、3 支 controller、
WS gateway 與整套測試——再加一個 CRUD 模組會讓它大到無法 review。

**代價要說清楚**：本 change 之後，後台仍然只能**從檢舉進到某個前台使用者**
（`add-admin-member-profile` 的 D6）。找不到沒被檢舉過的人、不能主動停權。
那個限制在第 5 項解除。
