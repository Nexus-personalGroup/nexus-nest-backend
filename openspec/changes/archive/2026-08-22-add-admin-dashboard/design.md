## Context

後台三個列表都是「去找特定的東西」，沒有一個回答「現在怎麼樣」。
這個 change 補上營運總覽，範圍由使用者定下：**定時快照、五個數字**。

它是 M4 裡唯一沒有現成模式可抄的一塊——前三個 change 的形狀都跟會員頁一樣，
而這一個要處理連線管理、重連與推送頻率。

## Decisions

### D1：定時快照，SSE 只是傳輸層

伺服器每 N 秒查一組數字推出去，**不是事件驅動**。

事件驅動要在每一則訊息、每一次連線上多做一份廣播——那是把儀表板的成本
加到**聊天的熱路徑**上，而那是最不該被拖慢的地方。儀表板看的是聚合數字，
晚 5 秒與晚 0 秒對「有沒有事」這個問題沒有差別。

**代價要認**：數字最多落後 N 秒，而使用者做完一個動作（例如處理掉一筆檢舉）
回到儀表板時可能還看到舊數字。因此畫面要標明「最後更新於 X 秒前」——
不標的話那幾秒會被當成 bug。

### D2：一個實例只跑一個 interval，不是一個連線一個

`N` 秒一次的查詢是**實例級**的：實例上有 1 個或 10 個管理員在看，
資料庫的查詢次數都一樣。查完的快照廣播給該實例上的所有訂閱者。

寫成「每個連線各自 setInterval」是最直覺的實作，而它會讓 10 個管理員
變成 10 倍的資料庫負載——**在一個為了「看有沒有事」而存在的頁面上**。
那種放大在開發時看不出來（自己只開一個分頁）。

沒有訂閱者時 MUST 停掉 interval：一個沒有人在看的頁面不該持續打資料庫。

### D3：`chat_messages` 的時間索引用 BRIN，不用 B-tree

「今日訊息數」需要 `WHERE created_at >= <今天>`，而 `chat_messages`
目前沒有 `createdAt` 索引——那是專案**最大的一張表**，每則訊息都要寫。

**選 BRIN 的理由**：`chat_messages` 是 append-only 且 `createdAt` 單調遞增，
物理順序與欄位值天然相關——那正是 BRIN 的適用條件。
它的索引大小是 B-tree 的千分之一量級，插入時的維護成本也遠低於 B-tree，
而這張表的寫入頻率是所有表裡最高的。

代價是 BRIN 走的是 bitmap heap scan 而非 index-only scan——
對「今天這一段連續區塊」的計數而言差異很小，因為要掃的正好是最後幾個區塊。

**實作時要驗證 Prisma 接受 `type: Brin`**；若這一版的 generator 不支援，
就退回 `@@index([createdAt])`（B-tree），並在 schema 註解裡記下原因——
退回是可接受的，但要留下痕跡，否則下次沒有人知道曾經考慮過。

**這是本 change 唯一的 migration。**

### D4：沿用 `BACKEND:MODERATION:VIEW`，不新增權限碼

儀表板顯示的是聊天營運的數字，而「能看聊天營運」就是 `MODERATION:VIEW` 的意思。

新增一個 `BACKEND:DASHBOARD:VIEW` 要動 seed、要調角色設定、
要讓每個既有角色重新配一次——換來的是**一個沒有人會單獨授予的權限**。
權限碼的價值在於它切出了真實的職責邊界，而這裡沒有新的邊界。

### D5：前端不能用 `EventSource`，要用 `fetch` + ReadableStream

**這是實作上最容易踩的一步。** 原生的 `EventSource` **無法帶自訂 header**，
而本專案的 access token 在 `localStorage`、以 `Authorization: Bearer` 傳送。

三條路，只有一條可走：

| 做法 | 為什麼不行 / 可行 |
| --- | --- |
| token 放 query string | **不行**。專案已明文禁止（WS 那邊寫過理由）：query 會進伺服器日誌、瀏覽器歷史與 `Referer`，等於把憑證寫進三個不受控的地方 |
| 改用 cookie 認證這一支 | **不行**。目前整條認證鏈是 Bearer，為一個端點開一條 cookie 路徑會讓兩套認證並存 |
| `fetch` + `response.body.getReader()` | **可行**。可以帶 header，自己解析 `data:` 行 |

代價是**重連要自己寫**（`EventSource` 內建，`fetch` 沒有）。
見 D6——而那個重連策略本來就需要自訂，內建的固定重連反而不夠。

### D6：重連要有退避，且斷線期間畫面要說實話

連線斷掉時（伺服器重啟、網路中斷、反向代理逾時）前端 MUST 重連，
但**MUST 有退避**：立刻重連在伺服器重啟期間會變成密集重試，
而那正是伺服器最脆弱的時刻。

斷線期間畫面 MUST 顯示「連線中斷，重新連線中」，
**MUST NOT 繼續顯示最後收到的數字而不做標示**——
一個停在 20 分鐘前的數字看起來與即時數字一模一樣，
而營運會依它做判斷。過期的資料要看得出來是過期的。

### D7：多實例下每個實例各自查，數字仍然一致

線上人數走 Redis（全域）、其餘四個走資料庫（全域），
所以任何實例查出來的快照都相同——不需要跨實例協調。

代價是**實例數 × 每 N 秒一次查詢**。以目前的部署規模這是可接受的；
若日後實例數變多，正確的做法是讓一個實例算完寫進 Redis、其餘讀快取，
而不是拉長 N（拉長 N 會讓所有人都看到更舊的數字來解決一個負載問題）。

### D8：待處理檢舉數要可點

五個數字裡只有它是**要人採取行動**的。可點導向 `/moderation/reports`，
讓「看到有 3 筆待處理」與「開始處理」之間沒有中斷。

其餘四個是狀態不是待辦，點了沒有明確的去處，因此不做成連結——
每個數字都可點會讓真正該點的那個失去區別。

## Open Questions

- **要不要顯示「本實例的連線數」**：多實例時它與「線上人數」不同
  （一個人可能多裝置、連在不同實例），對排查有用但對營運沒有。
  Prometheus 已經有這個指標，先不放進儀表板。
- **待處理檢舉數要不要分「超過 24 小時未處理」**：那是比總數更有行動意義的訊號，
  但需要先有實際的處理節奏資料才知道門檻該設多少。

## 為什麼不畫趨勢圖

畫趨勢要有時序資料，而這個專案**沒有存**。Prometheus 有，
但它是 scrape 模型——應用自己查不到歷史，除非再接一個查詢 API。

真的需要趨勢時，正確的做法是接 Grafana 讀 Prometheus，
而不是在後台重畫一次它已經畫得更好的東西。
在後台自建時序儲存則是把監控系統的問題搬進業務資料庫。
