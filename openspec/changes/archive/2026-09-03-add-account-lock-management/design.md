## Context

帳號鎖定的機制早就完整：登入失敗計數 → 達門檻寫 `members.locked_at` →
`APPLICATION_ACCOUNT_LOCK_DURATION_MIN` 之後自動到期 →
`POST /admin/security/unlock-account` 可提前解鎖。

**唯一缺的是「看得到」。** 這支只補那一塊，並刻意把 todo 上記載的範圍縮小
——縮小的理由要寫下來，否則下一個讀 todo 的人會以為有人做漏了。

## Goals / Non-Goals

**Goals:**

- 管理員能看到「現在有誰被鎖著」，不必等使用者來反應。
- 列表上的「鎖定中 / 已到期」判定與登入時的判定**是同一份規則**（見 D3）。

**Non-Goals:**

- **不新增解鎖端點**（見 D1）。
- **不做手動鎖定**（見 D2）。
- 不建鎖定歷史表——目前沒有「這個人這個月被鎖過幾次」的需求，
  而為了它建一張表是先做了再找用途。

## Decisions

### D1：不新增 `DELETE /locks/:id`，解鎖沿用既有端點

todo 記載的範圍含 `DELETE …/:id`。不做，因為它與
`POST /admin/security/unlock-account` **是同一個動作**，差別只在吃 id 還是 email
——而列表頁本來就會拿到 email。

**兩支做同一件事的端點，代價不是多一支程式碼**：它們會各自演化
（一支加了稽核、另一支沒有），而呼叫端要選一個，選錯了不會有人發現。

也考慮過反過來——用 `DELETE /locks/:id` 取代舊端點，讓 REST 語意一致。
不選，因為那要推翻 `api-security-management` 已寫入的端點契約，
而**那支端點是 `fix-unauthenticated-surface` 為了解決「帳號鎖定沒有復原路徑」
才加上的**。為了語意整齊而動它，收益不成比例。

### D2：不做手動鎖定（`POST /locks`）

手動鎖定要回答一個問題：它跟停用帳號（`status = false`）差在哪？

| | 鎖定 | 停用 |
| --- | --- | --- |
| 誰觸發 | 系統（登入失敗達門檻） | 管理員 |
| 怎麼結束 | **時間到自動解開** | 管理員再打開 |
| 意圖 | 擋暴力破解 | 擋這個人 |

管理員按下「鎖定」時的意圖幾乎一定是後者，而他拿到的是前者——
**一個 N 分鐘後自己失效的封鎖**。那不是少一個功能，是給錯工具。

### D3：到期判定必須與登入路徑共用同一份規則

`members.locked_at` 只是時間戳，「還鎖著嗎」要靠
`locked_at + APPLICATION_ACCOUNT_LOCK_DURATION_MIN` 算。那個計算目前在
`PrismaAccountLockAdapter.checkLock`。

**列表不得自己算一次。** 兩份計算會漂移，而漂移的症狀是
「列表說鎖著、但那個人登得進去」——看起來像資料不同步，實際是兩份規則。
因此列表查詢放進 `AccountLockPort`（同一個 adapter 實作），
而不是塞進 member 的持久層 port。

### D4：列表預設只顯示「鎖定中」，但「已到期」查得到

`locked_at != null` 的列包含**已經到期、只是還沒被清掉**的帳號
（清除發生在下次登入或解鎖時）。這些人現在登得進去，把他們列成「鎖定中」是錯的。

- 預設過濾為**鎖定中**——管理員打開這一頁時問的是「現在有誰被鎖著」。
- 但保留 `status=expired` / `all` 讓「這個人今天被鎖過」查得到。
  沒有鎖定歷史表，這是唯一能回答那個問題的地方。
- 每一列 MUST 顯示狀態，MUST NOT 只顯示 `lockedAt` 讓人自己心算。

### D5：已到期的列不得提供解鎖按鈕

既有的 `UnlockAccountService` 對非 `LOCKED` 狀態回 409
（`AccountNotLockedException`）——那是刻意的，避免靜默通過一個沒有效果的操作。

因此列表上**已到期的列必須不提供解鎖**，而不是提供了再讓它 409。
按下去必定失敗的按鈕比沒有按鈕更糟：使用者會以為是系統壞了。

**用 disabled 而非隱藏**：這是列內動作，依
`platform-frontend-conventions` 的「動作控制項的權限呈現規則」——
不過那條規則講的是權限，這裡是資料狀態。**資料狀態的規則相反：disabled + 說明。**
所以已到期的列**顯示 disabled 的解鎖並註明「已自動解鎖」**，
讓管理員知道「這個人已經可以登入了」而不是「功能不見了」。

### D6：回應要帶 `lockEnabled`（實作過程中才發現的）

寫完之後做實機驗收，把一個帳號的 `locked_at` 設成兩分鐘前、再用它登入——
**登入成功了**。查下去：`APPLICATION_ACCOUNT_LOCK_ENABLED` 預設 `false`，
而 `LoginService` 檢查鎖定、記錄失敗、寫入鎖定三處**全部包在那個 flag 底下**。

也就是說：**預設部署下系統永遠不會產生鎖定紀錄**，這一頁會永遠是空的，
而空狀態寫著「目前沒有帳號被鎖定」——那在此時是**錯的**。
不是沒有人被鎖，是根本不會鎖，而兩者在畫面上長得一模一樣。

修法是讓列表端點回傳 `lockEnabled`，前端據此顯示停用提示。
**不另開一支 flag 端點**：需要這個值的只有這一頁，而它本來就要呼叫這支；
前端目前也沒有任何讀取 feature flag 的管道，為此建一套基礎設施
比問題本身大得多。

**這件事驗收前看不出來**——單元測試、e2e、型別全都會過，
因為它們驗的是「列表正確反映 `locked_at`」，而那是對的。
錯的是「`locked_at` 從哪來」這個前提。

## Risks / Trade-offs

- **範圍比 todo 記載的小。** 已在 proposal 與本文件寫明理由，
  並會在 todo 的完成紀錄裡註明「D1 / D2 縮小了範圍」，避免看起來像做漏。
- **這一頁在預設設定下是空的**，因為帳號鎖定預設關閉（見 D6）。
  已用 `lockEnabled` + 停用提示讓它看得出來，但**功能本身要不要預設開啟
  是另一個決定**，不在本 change 的範圍。

- **沒有鎖定歷史。** `locked_at` 被清掉之後那次鎖定就消失了。
  D4 的「已到期」查詢能涵蓋「清掉之前」的窗口，但不是完整歷史。
  真的需要時要另建表，屆時本頁是自然的入口。
- **新增 endpoint 需要 `swagger:bundle` + `api-client generate`**，
  漏跑會讓前端拿不到型別。
