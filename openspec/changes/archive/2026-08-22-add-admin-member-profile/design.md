## Context

`add-admin-moderation-ui` 把審閱動線接起來了，但只有「從檢舉查到人」這個方向。
反方向——從人查到他做過什麼——目前只有詳情頁角落那段時間軸。

這個 change 補上另一半，並第二次面對同一個權限問題：
**審閱要看的成員資料，全部在帳號管理的權限後面**。
上一次的答案是「在審閱側補它自己要的欄位」，這次沿用同樣的判準。

## Decisions

### D1：新端點回審閱視角的子集，不是轉發帳號管理的 DTO

`GET /moderation/members/:memberId` 只回七個欄位：email、啟用狀態、加入時間、
在線狀態、被檢舉次數、提出檢舉次數、聊天室數。

**不回角色、不回權限、不回最後登入 IP、不回密碼相關的任何欄位。**
判準是「審閱要回答什麼問題」：他是誰、他還能不能用、他被檢舉多少次、他現在在不在。
角色與權限回答的是「他能做什麼」——那是帳號管理的問題，而
`BACKEND:ACCOUNT:VIEW` 存在的理由正是把那個問題圈起來。

最容易犯的錯是「反正 `loadMemberById` 都查回來了，順手全部回傳」。
那種洩漏在 code review 時看起來只是「多回幾個欄位」，而它繞過的是一整條權限邊界。
上個 change 已經為此寫了一支 e2e（列表只帶 email 不帶其他帳號資料），這裡比照。

### D2：聊天室清單直接複用 `listByMember`，但要意識到語意變了

前台的「我的房間」用的就是 `ChatRoomRepositoryPort.listByMember()`，
查詢條件完全相同——差別只在**誰在問**。

複用是對的：同一個查詢寫兩份，日後改了一份忘了另一份就會產生兩種「房間清單」。
但要記得授權的來源不同：前台那條是「你只能查自己的」（memberId 來自 token），
後台這條是「你有 MODERATION:VIEW 就能查任何人的」（memberId 來自 path）。

**因此 memberId 絕對不可以來自 body 或 query 的可選欄位**——
那會讓前台的路徑有機會傳入別人的 id。path 參數配上明確的 guard 是唯一安全的形狀。

### D3：在線狀態是查詢當下的快照，不做即時更新

`PresencePort.isOnline()` 讀 Redis，回傳的是**送出回應那一刻**的狀態。
畫面不輪詢、不接 SSE。

理由是這個數字的用途：停權之前想知道「他是不是正在活動」。
那是一個粗略的判斷，不需要秒級精確。而做成即時的成本是一整套推播機制，
換來的是一個小圓點的顏色更準一點。

**畫面上要標明它是查詢當下的狀態**，否則使用者會以為它是即時的，
然後在它沒有變化時懷疑系統壞了。

### D4：檢舉次數用 count 查，不是把清單抓回來算長度

被檢舉次數與提出檢舉次數各是一次 `count`，走既有索引
（`idx_chat_reports_target_member`；`reporterId` 走 `uq_chat_reports_reporter_message`
的前綴）。

用「抓清單再 `.length`」的寫法在測試資料上完全正常，而在一個被檢舉 500 次的帳號上
會把 500 筆資料撈進記憶體只為了得到一個數字。這類問題不會有人回報——
它只是讓某些頁面偶爾比較慢。

### D5：概覽頁不寫稽核

概覽與相關檢舉列表**都不含 `contentSnapshot`**，因此不寫稽核——
與檢舉佇列的處理一致：稽核量要與「實際看到敏感內容的次數」對齊，
而不是與「點了幾下」對齊。

從概覽點進某一筆檢舉詳情時，那一次會照常寫 `REPORT_VIEWED`。

### D6：進入點只有檢舉，不做成員搜尋

概覽頁的 memberId 從檢舉來。**不提供以 email 搜尋成員的端點**，
因為「能列舉所有使用者」本身就是一種帳號資料存取，
與 `BACKEND:ACCOUNT:VIEW` / `BACKEND:MODERATION:VIEW` 拆開的初衷有張力。

這也符合實際動線：審閱從來都是從檢舉開始的，不是逐人巡查。

**要誠實記下的取捨**：有 `MODERATION:VIEW` 的人只要手上有一個 UUID
就能查任何成員的概覽——沒有「必須先有檢舉」的檢查。加那個檢查會讓
「查一個剛被停權的人」這種正當操作失敗，而它擋不住真正想濫用的人
（他可以先從任何一筆檢舉拿到 id）。授權模型就是「審閱人員可以查看成員的審閱資訊」，
這一點寫在 spec 裡，不要靠讀程式碼推斷。

## Open Questions

- **被檢舉次數要不要限定時間範圍**：「最近 30 天被檢舉 5 次」比「歷史上被檢舉 5 次」
  更有判斷價值，但範圍怎麼定要看實際資料。先做全部歷史，等佇列跑一陣子再看。
- **要不要顯示「這個人檢舉別人的準確率」**（提出的檢舉中有多少被判定成立）：
  那是一個很強的訊號——用來識別濫用檢舉的人——但需要先累積判定資料才有意義。

## 為什麼不順手加 `senderId` 索引

「他發了幾則訊息」是最直覺會想放進 360 視圖的數字，但 `chat_messages`
沒有 `senderId` 索引，算它是全表掃描。

加索引本身不難，但那是**為了一個統計數字在最大的一張表上多一份寫入成本**——
每一則訊息的寫入都要維護它。而這個數字對判定的幫助遠小於「他被檢舉幾次」：
發得多不代表發得糟。

真的需要時再加，那時應該連帶想清楚它還要服務哪些查詢。
