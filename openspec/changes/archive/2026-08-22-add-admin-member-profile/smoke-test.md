# add-admin-member-profile 手動驗證

前置：`pnpm dev`，用有 `BACKEND:MODERATION:VIEW` 的帳號登入後台，
至少要有一筆檢舉（沒有的話見 `add-admin-moderation-ui` 的 smoke-test）。

## 1. 從檢舉點進當事人

進 `/moderation/reports` → 點任一筆的「檢視」→ 在詳情頁點「被檢舉人」的 email。
預期導向 `/moderation/members/<id>`，五個區塊都在：
基本資料、檢舉統計、相關檢舉、所在聊天室、行為紀錄。

「檢舉人」同樣可點——濫用檢舉的人也需要被查。

## 2. ⭐ 返回要回到原本的位置

**這一項 CI 驗不到。**

從檢舉詳情進到概覽後按「返回」，預期回到**那一筆檢舉詳情**，而不是佇列。
寫死回佇列的話，審閱者每看一次當事人就要重新找回原本那筆——
而他多半正在一連串檢舉中間。

再測一次：直接把概覽的網址貼進瀏覽器（沒有上一頁）→ 返回鍵不該讓畫面壞掉。

## 3. 側邊欄沒有這一頁

確認 Sidebar **沒有**「成員概覽」之類的項目。

概覽沒有列表可以進入——審閱人員看不到成員清單（那需要帳號管理權限），
一個點進去只會看到「請提供 ID」的選單項目比沒有更糟。

## 4. 兩個方向的檢舉分開

在「相關檢舉」區塊切換「被檢舉」／「提出的」：

- 兩邊的**對造**不同：查被檢舉時對造是檢舉人，查提出的時對造是被檢舉人
- 對造**不是這個人自己**——若每一列都印同一個 email 就是接錯了
- 切換後網址帶上 `?role=REPORTER`，重新整理後保持
- 點任一列 → 回到該筆檢舉詳情

## 5. 停權要看得出來

用審閱頁把某個成員停權，然後進他的概覽。預期標題旁有明顯的「已停權」標記，
不只是基本資料裡的一行文字。

順手驗證統計：停權前後「被檢舉」的數字不變（停權不會改變檢舉紀錄）。

## 6. ⭐ 在線狀態標明是「查詢當下」

概覽的連線狀態應顯示「查詢當下：在線／離線」。

不標明的話使用者會以為它即時，然後在它長時間不變時懷疑系統壞了。
可以開一個前台連線再重新整理概覽頁確認它會變——**但它不會自己變**，那是設計。

## 7. ⭐ 相關檢舉列表不會 prefetch 詳情

**這一項 CI 驗不到，要看 DevTools 的 Network。**

在概覽頁把滑鼠移過「相關檢舉」的每一列（不要點）→ 確認**沒有**任何
`reports/<id>` 請求。點進去才會寫 `REPORT_VIEWED` 稽核。

順便確認概覽本身**不寫稽核**：

```sql
SELECT action, count(*) FROM chat_audit_logs GROUP BY action;
```

反覆重新整理概覽頁，`REPORT_VIEWED` 的數字不該增加。

## 8. 帳號已刪除的對造

把某筆檢舉的對造軟刪除（`UPDATE members SET deleted_at = NOW() WHERE id = '<對造 id>'`），
回概覽的相關檢舉列表，確認該列顯示「已刪除的帳號（尾 8 碼）」而不是空白，且該列仍在。

**不要刪自己正在使用的帳號**——那會讓 token 失效，症狀是整頁 401，
而錯誤訊息完全指不到原因（實作時踩過）。驗完記得改回 `deleted_at = NULL`。
