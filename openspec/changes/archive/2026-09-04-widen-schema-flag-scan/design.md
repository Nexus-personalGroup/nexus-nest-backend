## Context

守則 `openspec-schema.spec.ts` 有一條「建立 change 的指令一律帶 `--schema`」，
掃描範圍是 `walk('.claude')`。那個範圍是**當初問題發生的地方**
（skill 與 command 各有一份 propose 流程），不是「所有可能出問題的地方」。

第三份真相後來長在 `openspec/project/openspec-conventions.md`——
而那正是 `CLAUDE.md` 指定的慣例來源。

## Goals / Non-Goals

**Goals:**

- 掃描範圍涵蓋**所有會教人怎麼建 change 的現行文件**。
- 封存的歷史不因規則改變而變紅。

**Non-Goals:**

- 不改正則、不改旗標名稱、不動 opsx 薄殼那條規則。
- 不處理「文件之間內容重複」這個更大的問題（見 D3）。

## Decisions

### D1：範圍以「是不是現行的指示文件」為判準，不是目錄長相

擴大的四個位置——`.claude/`、`openspec/`、`CLAUDE.md`、`README.md`
——共同點是**有人會照著它做**。判準寫成這句話而不是列目錄，
之後新增的指示文件才知道該不該進來。

`tasks/` 不列入：`todo.md` / `lessons.md` 記的是狀態與教訓，不是操作指示。
（`lessons.md` 現在就有一處散文提及 `openspec new change`，
正則不會誤判，但即使會，那也不該被當成指示。）

### D2：封存區明確排除，而且要寫在需求裡

`openspec/changes/archive/` 目前沒有任何真正的呼叫，所以現在納不納入都是綠的。
**但仍然要明確排除**：封存的是當時的決策紀錄，
而「今天的規則讓昨天的紀錄變紅」會逼人去改歷史，那比漏掉一條檢查更糟。

⚠️ **這也決定了掃描範圍要取整個 `openspec/` 而不是只取 `openspec/project/`。**
只掃 project 的話，封存區根本不在路徑上，這條排除就是**永遠碰不到的死程式碼**——
而「在封存區塞一筆違規仍然綠」的反向驗證也會通過，只不過是因為沒掃到，
不是因為排除生效。**實測過**：拿掉排除那一行，同一筆注入立刻被抓出來。

這一點如果不寫進需求，下一個擴大範圍的人會理所當然地把 `openspec/` 整個掃進去。

### D3：不處理「三份文件講同一件事」的根本問題

真正的根因是**建 change 的指令在三個地方各寫一次**
（skill、opsx command、conventions 文件）。理想解是只留一份、其餘轉引用。

**不在這支做**：`opsx` 的薄殼已經是那個方向的成果，
而 `openspec-conventions.md` 是給人讀的慣例說明，把指令抽走會讓它變得難讀。
擴大掃描範圍是**承認會有多份、但每一份都要正確**的務實解。

代價誠實標記：多份文件仍然可能在**其他方面**漂移（例如流程步驟），
這條守則只保證那一個旗標。

## Risks / Trade-offs

- **掃描範圍變大 = 誤判面變大**。緩解是正則不變（只認 `openspec new change`
  後面接引號或 `<` 的真正呼叫），且擴大後現況直接綠——已實際確認過。
- **`README.md` 目前沒有那個指令**，納入是預防性的。
  代價是規則涵蓋了一個空集合，好處是那份文件被加上指令時不必記得回來改守則。
