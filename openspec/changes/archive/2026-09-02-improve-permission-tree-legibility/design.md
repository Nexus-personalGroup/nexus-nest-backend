## Context

權限樹是「把後端的授權模型攤給人看」的地方，而它目前攤得不完整也不一致：
標題是英文碼片段、名稱停留在改版前的用語、而**整個安全管理區塊根本不在上面**。

三者的共同點是**它們都不是後端的 bug**——9 個權限碼、5 個模組、
`@Roles(SUPERADMIN)` 的安全例外，每一個都有它的理由且理由都成立。
壞掉的是這些理由**在 UI 上一個都看不出來**。

因此這個 change 的原則是：**不改授權模型，只改它的可見性**。
唯一的例外是 `PERMISSION_CATALOG` 的 `name` 字串——那本來就是顯示用的。

## Goals / Non-Goals

**Goals:**

- 權限樹上的每個字都是中文，且用語與側邊欄一致。
- 「這個功能存在但不可指派」在 UI 上看得出來，而不是看起來像漏掉。
- 「什麼時候 disabled、什麼時候隱藏」有單一答案，且有守則守著。

**Non-Goals:**

- **不動任何守衛**。`SecurityController` 維持 `@Roles(SUPERADMIN)`（見 D2）。
- **不新增或移除權限碼**。`ATTACHMENT` 的處置見 D4。
- 不重新設計權限樹的版面（卡片、全選按鈕、滾動容器都不動）。

## Decisions

### D1：模組中文對照表放前端，不擴充 API

群組標題目前是 `parsePermissionCode` 從 `BACKEND:ACCOUNT:VIEW` 切出來的
`BACKEND` 與 `ACCOUNT`。要中文化有三條路：

| | 做法 | 為什麼不選 |
| --- | --- | --- |
| A | 前端 `MODULE_LABELS` 對照表 | **選這個** |
| B | 後端 `PERMISSION_CATALOG` 加 `moduleName`，API 多回欄位 | 動到回應契約 → swagger yaml + `api-client generate` + `api-role-management` 的回應規格全部要改，而這個標籤**只有一個畫面在用** |
| C | 直接切 `name`（「後台-管理者帳號-檢視」前兩段就是中文） | 把顯示綁死在字串格式上。有人寫了一個沒有連字號的 `name`，畫面就壞掉而且不會有人發現 |

選 A 的代價是**兩份知識**：後端有模組碼、前端有它的中文。
漂移的形式很具體——後端加一個新權限碼，前端沒加對照，標題就退回英文。
**因此 A 必須配一支守則**（見 D6），否則它就是下一個「文件與程式碼各說各話」。

「後端擁有分類法，所以後端該擁有標籤」這個論點成立，B 在原則上比較對。
不選它的理由是**成本與收益的比例**：為了一個標籤讓 API 契約、swagger、
api-client 三份東西一起動，而守則能以十分之一的成本擋掉同樣的風險。

### D2：安全管理維持 SUPERADMIN，但必須出現在權限樹上

一度打算新增 `BACKEND:SECURITY:VIEW/EDIT` 並把 `SecurityController` 改成
`PermissionsGuard`。**查到 `api-security-management` 的 Purpose 之後放棄**——
那不是遺漏，是寫下來的決定：

> 安全設定屬於「不該用權限碼細分」的一類：能改 IP 名單等同能繞過所有 IP 層防護，
> 不存在只給一半的合理情境。

而且 `PermissionsGuard` 沒有任何 SUPERADMIN 特例（查過原始碼），所以改守衛
**是行為變更而不是重構**：拿到 `SECURITY:EDIT` 的自訂角色可以把自己的 IP
加進白名單、解掉封鎖、解鎖被鎖住的帳號。IP 層防護會形同虛設。

但使用者原本的觀察是對的——**權限樹上看不出這個功能存在**。
那個問題不需要靠下放權限來解：在樹上放一個**不可指派**的區塊即可。
使用者看得到功能存在、看得到為什麼給不了，安全模型一行都不用動。

**清單寫死在前端**（IP 白名單 / IP 黑名單 / 帳號解鎖），因為這三項在後端
沒有對應的權限碼，`GET /roles/permissions` 不會回它們。這同樣是兩份知識，
同樣配一支守則（見 D6）。

### D3：disabled 與隱藏的分界——依控制項的層級，不依動作的種類

現況是兩種做法並存，而 spec 自己也給了兩個答案：

> 使用者沒有 `BACKEND:ROLE:EDIT` 權限：整個 dropdown 不顯示，**或**編輯項 disabled。

「或」就是漂移的許可證。定成單一答案：

| 層級 | 例子 | 規則 | 理由 |
| --- | --- | --- | --- |
| **列內動作** | 表格每一列的編輯 / 刪除 | **隱藏** | 每列一顆，20 列就是 40 顆點不下去的灰按鈕。它們不傳遞資訊，只製造噪音 |
| **頁面級動作** | 「新增角色」「新增管理者」 | **disabled + tooltip** | 整頁只有一顆。灰著是在說「這裡有這個功能，你缺 X 權限」——那正是使用者需要知道的 |
| **處置動作** | 停權、移除訊息、判定檢舉 | **disabled + tooltip** | 同上，且 `ui-moderation` 已明文要求，理由是「隱藏會讓人以為功能不存在」 |

**這個分界不是新規則，是把現況寫下來**：`RolesTable.tsx` 與 `MembersTable.tsx`
早就是隱藏，`FrontUserActions` / `ReviewForm` / `ReportActions` 早就是 disabled。
本 change 不改任何一行行為，只是讓下一個人不必重新猜。

**不選「全部隱藏」**：只有檢視權限的人會看到一個功能較少的後台，
而且無從得知自己缺什麼、該去要什麼。
**不選「全部 disabled」**：列內動作會把表格變成灰按鈕牆。

### D4：`ATTACHMENT` 留在樹上，不移除

`BACKEND:ATTACHMENT:EDIT` 有守衛（`AttachmentController` 兩支端點在用），
但 `apps/web` 沒有任何附件頁面，所以在後台勾了它看不出差別。

**不移除**，兩個理由：它是真的在保護一組端點（移除等於讓那兩支端點失去授權來源
或退回全開）；而附件管理頁是路線圖上的東西（見 `tasks/todo.md`「附件訊息」），
移掉之後要記得加回來，而那種「記得」正是本專案反覆失守的地方。

代價是樹上有一個目前看不出效果的項目。**這個代價寫進註解**，
不加「（尚無對應頁面）」之類的 UI 文字——那會變成需要跟著功能上線而更新的字串，
而沒有任何東西會提醒你去改它。

### D5：`MODERATION` 一個碼管三個頁面，維持不拆

營運總覽 / 檢舉審閱 / 聊天室三個側邊欄項目都吃 `BACKEND:MODERATION:VIEW`。
與「一個模組一組權限」的直覺不符，但拆開需要一個「只給看檢舉、不給看聊天室」
的真實場景，而那個場景不存在——三個頁面是同一件事的三個視角。
拆了只會讓每次授權多勾兩次。

群組標題因此叫「聊天管理」而不是「檢舉審閱」，與側邊欄的分組名一致。

### D6：兩支守則，各擋一種漂移

D1 與 D2 都用「前端寫死一份知識」換成本，兩者的漂移形式不同，所以是兩支：

1. **模組中文對照必須齊全**：`PERMISSION_CATALOG` 出現的每個 module
   都要在前端對照表裡有值。新增權限碼卻忘了加中文時失敗。
2. **不可指派清單必須與後端一致**：`SecurityController` 仍為
   `@Roles(RoleCode.SUPERADMIN)`。有人把它改成 `@Permissions(...)` 時失敗——
   因為那一刻前端「限超級管理者」的說明就變成謊話。

第 2 支刻意**不去比對條目內容**（不檢查「IP 白名單 / IP 黑名單 / 帳號解鎖」
這三個字串），只檢查守衛沒變。比對字串會需要一份端點與中文名的對照，
那是第三份要維護的知識，而它擋下的是文案不精確——不值得。

## Risks / Trade-offs

- **前端存了兩份後端知識**（模組中文、不可指派清單）。守則擋得住「後端變了前端沒跟」，
  擋不住「兩邊都改但改得不一致」。接受——後者需要人為同時改兩個地方，
  而那時人已經在看這兩份東西了。
- **`name` 改字串要重跑 seed**。`seed-permissions` 是 `alwaysRun` 且是 upsert
  （`update: { name, ... }`），所以重跑會更新既有列。**但不重跑的話 DB 裡還是舊名稱**，
  而畫面讀的是 DB——會出現「程式碼改了、畫面沒變」。寫進 tasks 的驗收步驟。
- **不可指派區塊是純展示**，勾不動也不會送出。若日後真的要下放安全權限，
  這個區塊要換成一般區塊，而不是在它上面疊條件。
