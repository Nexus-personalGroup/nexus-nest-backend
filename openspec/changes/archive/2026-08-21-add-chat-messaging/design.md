## Context

`add-chat-rooms` 留下的地基：房間、成員關係、`ENSURE_ROOM_MEMBERSHIP_USE_CASE`（成員資格判斷的單一來源）、`EventPublisherPort`（跨實例送出）。這個 change 只加訊息，不動上述任何一項的語意。

範圍是使用者選定的：**純文字訊息 + 已讀回條**。撤回與附件**確定要做，只是不在這個 change**——因此下方有一節專門檢查現在的決定會不會擋住它們。

## Decisions

### D1：送訊息走 WebSocket，不走 REST

送訊息與收訊息走同一條連線。伺服器寫入成功後回 `server:messageAck`（帶伺服器產生的 `messageId` 與 `seq`），同時向房間廣播 `server:messageCreated`。

**為什麼不走 REST**：REST 的優勢是重試、冪等、離線佇列都有現成慣例，而 HTTP 的每次請求要多一次連線層往返。但真正的決定因素不是延遲——是**狀態一致性**。走 REST 送、WS 收的話，送出者會有兩條路徑拿到自己那則訊息（HTTP 回應與 WS 廣播），客戶端必須自己處理「哪個先到」與「會不會顯示兩次」。走同一條連線就只有一個順序。

**代價要認**：離線佇列與重試得由客戶端自己做，而不是沿用 HTTP 的既有機制。這是把複雜度從伺服器移到客戶端，不是消除它。

**為什麼不兩條都開**（使用者也否決了）：同一件事有兩個入口，去重與限流都要在兩邊各接一次。這正是最容易長出「兩份實作漸漸不一致」的形狀——而不一致的症狀會是「用某個路徑送的訊息不受限流」，沒有人會主動發現。

### D2：`seq` 由房間上的計數器產生，不用時間戳也不用資料庫序列

`ChatRoomRecord` 加一個 `lastSeq` 欄位，寫訊息時在同一個交易內 `UPDATE … SET last_seq = last_seq + 1 RETURNING last_seq`，把結果寫進訊息列。

**為什麼不用 `createdAt` 排序**：兩個實例同時寫入可能落在同一毫秒，時間戳無法決定順序；更糟的是不同客戶端各自排序會得到不同結果。**順序必須由伺服器決定並固定下來**，不能留給讀取端推導。

**為什麼不用 PostgreSQL sequence**：sequence 是資料庫層級的物件，一個房間一個 sequence 代表房間數等於 schema 物件數——建房間變成 DDL 操作，而 DDL 不能安全地跟 DML 放在同一個交易裡。

**為什麼不用全域遞增 ID**：全域單調不代表房間內連續。補齊要能問「seq 大於 N 的都給我」，房間內有洞的話客戶端無法判斷「這是被跳過的號碼還是漏收的訊息」。

`UPDATE … RETURNING` 會對該房間的列取鎖，因此同一房間的併發寫入是序列化的。這是刻意的：**每則訊息都要拿到唯一且連續的號碼，那本來就無法平行**。房間之間互不影響，所以吞吐的瓶頸是「單一房間的寫入速率」，不是全站。

### D3：去重用 `(roomId, clientMessageId)` 唯一索引，撞到就回傳既有訊息

客戶端在送出前產生 `clientMessageId`（uuid），重試時沿用同一個。伺服器撞到唯一索引時，查出既有訊息並回一個**與首次成功時完全相同的 ack**。

這與 `add-chat-rooms` 的 `directKey` 是同一個模式，理由也相同：**「先查有沒有」與「寫入」之間有空窗**。差別在於這裡的競態更常發生——重試通常在數百毫秒內，而且兩次請求可能落在不同實例上。

**去重範圍限定在房間內**而非全域：`clientMessageId` 由客戶端產生，全域唯一索引等於信任所有客戶端不會產生碰撞。限定在房間內時，惡意客戶端最多只能影響自己所在的房間。

**ack 必須在寫入成功之後才送**。樂觀回覆（先 ack 再寫）在寫入失敗時會讓使用者看到一則實際不存在的訊息，而且沒有任何回頭修正的機會——客戶端已經把它畫在畫面上了。

### D4：補齊用 `lastSeq` 而非時間

重連後客戶端送 `client:syncRoom { roomId, lastSeq }`，伺服器回傳該房間 `seq > lastSeq` 的訊息。

**為什麼不用時間**：客戶端的時鐘不可信，而且「我最後收到的那則的時間」與「伺服器寫入的時間」本來就不同。`seq` 是伺服器產生的、房間內連續的——客戶端只要記住最後一個號碼就能精確表達「我看到哪裡」。

**補齊有上限**（一次最多 N 則）。回應要帶 `hasMore`，讓客戶端知道還沒補完而不是誤以為斷線期間只有這幾則。**沒有這個旗標的話，「補齊上限」會靜默地變成「丟訊息」**——這正是這個 change 要防的三件事之一，不能自己再製造一次。

離線太久（超過保留範圍）的情況這次不處理，但 `hasMore` 讓客戶端至少能察覺並改用歷史查詢。

### D5：已讀位置存 `lastReadSeq`，不存「哪幾則已讀」

每人每房間一列，記最後讀到的 `seq`。已讀是單調前進的——不需要記錄集合，也不接受倒退（客戶端往回捲不代表未讀）。

未讀數由 `room.lastSeq - read.lastReadSeq` 算出，不另存欄位：**存下來就要在每次寫訊息時更新所有成員的未讀數**，那是一次寫入放大成 N 次，而它可以被算出來。

## Open Questions

- **訊息保留期限**：目前沒有清理機制，訊息無限增長。M3 的監控會需要保留原始訊息以供檢舉調查，因此保留策略應該與檢舉功能一起決定，不在這個 change 猜。
- **限流的閾值**：先給一個保守預設（每人每房間每 10 秒 20 則），實際值等有真實使用資料再調。閾值進環境變數就是為了不必改程式碼調整。

## 為之後的兩項預留了什麼

撤回與附件確定要做。這裡逐項檢查現在的決定會不會擋路——**不預先建欄位**（那是替沒寫的功能猜規格），但要確認之後加得上去：

### 撤回 / 刪除訊息

之後加 `deletedAt` nullable 欄位即可，不需改動任何既有欄位。

**現在就要注意的一點**：補齊（D4）與歷史查詢回傳的是「`seq` 大於 N 的訊息」。訊息被撤回後**那一列必須留著**，否則 `seq` 會出現洞，而客戶端無法區分「這個號碼被撤回了」與「我漏收了」。因此撤回一定是軟刪除——這與房間成員關係刻意不做軟刪除的決定不衝突，兩者的理由不同：成員關係重新加入就是新關係，而訊息的「曾經存在過」本身就是要同步給所有人的資訊。

這一點寫在這裡，是因為它是**現在的設計對未來的約束**，不是未來才要想的事。

### 附件訊息

之後加 `messageType` 欄位（預設 `TEXT`）與附件關聯。現在的 `content` 是 `TEXT NOT NULL`，附件訊息可以用 `messageType = ATTACHMENT` 搭配 content 存說明文字，不需要把既有欄位改成 nullable。

真正要先想清楚的是前台的上傳授權與容量限制——那與訊息本身無關，屬於獨立主題，因此它獨立成一個 change 是對的切法。

## 實作過程中的修正

### 限流守則改為「表態式」，不猜哪些 handler 會寫入

proposal 原本寫的是「**會寫入的** WS handler 必須限流」。實作時發現那要守則自己判斷
哪些 use case 是寫入型，而唯一可行的判斷是動詞前綴（Send / Create / Update…）。
`ToggleReactionUseCase` 這種命名就會靜默漏掉。

改成：**呼叫 use case 的 handler 都要表態**——接上限流，或列入豁免並寫理由。
判定函式做成吃字串的純函式（`resolveService` 由呼叫端注入），因此六個判定
都有合成輸入測試釘住，包含「找不到 service 檔時視為未表態」這個容易寫成靜默略過的分支。

這個形狀本專案已經吃過三次虧（`layering` 只掃 `*Controller.ts`、`authorization-coverage`
看不到 WS、`includes()` 分不出使用與提及），差別在於前三次都是**事後**才發現。

### 順手釘住 `openspec/config.yaml`

`openspec new change` 會產生這個檔案，預設值是內建的 `spec-driven` 而非本專案的
`spec-driven-custom`——它一出現就是錯的，而且 change 照樣建得起來、`openspec validate`
照樣過，只是格式規範全部不生效。已改指向 custom 並補守則釘住（兩種失效模式都反向驗證過）。

### 新增 `RATE_LIMITED` 這個 domain exception kind

既有的 kind 沒有對應 429 的語意，借 `LOCKED` 會回 423。因此這次**有動到**
`GlobalExceptionFilter` 的 kind → status 對照表——那是「新增 exception 不用動 filter」
的例外：新增 **kind** 要動，新增 exception 不用。
