## Context

專案審查報告的問題 2。這是 `add-admin-dashboard` 留下的錯，而它違反的是
`cache-keys.ts` 自己寫下的約束——「規則寫在註解裡，而註解不會失敗」。

修法本身不難，難的是**不要在修的過程中違反另一條既有規則**：
`platform-websocket-transport` 明文禁止「以集合成員形式儲存連線而不帶各自的時效」，
而這個 change 要加的正好是一個 SET。D1 就是在處理這件事。

## Decisions

### D1：加的是「衍生索引」，連線紀錄本身完全不動

既有 spec 寫得很明確：

> 每筆連線紀錄 MUST 帶有最後心跳時間……以「集合成員」形式儲存而不帶各自的時效
> MUST 視為違反本需求——那會讓被 kill 的實例上的使用者永遠顯示為在線。

新加的 SET **不是連線紀錄**，是「目前有在線連線的成員 ID」的索引。
連線仍然存在各自的 Hash 裡、仍然帶心跳時間、仍然由 TTL 與 sweep 回收——
**真相沒有換地方**，只是多了一份可以 O(1) 讀出基數的投影。

**這個區別必須寫進 spec**，否則日後有人看到 presence 相關的 SET，
會以為當初那條規則被打破了，然後花時間去查一件沒發生的事。

判準是：**SET 壞掉時，系統會不會給出錯的在線判斷？** 不會——
`isOnline()` / `getConnections()` 讀的仍然是 Hash。SET 只影響「總數」這一個數字，
而它有校正機制。

### D2：漂移用 sweep 的既有遍歷校正，不用計數器

審查報告建議 `markOnline` / `markOffline` 增減一個計數器。**不採納。**

計數器的漂移方向是**單向累積**的：實例被強制終止時 `markOffline` 永遠不會執行，
計數只增不減。而「由 sweepStale 順便校正」對計數器而言不成立——
要知道正確的計數就得先知道正確的集合，也就是還得掃一次。

SET 不同：`sweepStale` **本來就在遍歷所有 presence key**，遍歷過程中自然知道
「哪些成員還有未逾時的連線」——那就是真值。校正因此是那個迴圈裡的順手一步。

**校正用差集而非整份覆寫**：
- 在 SET 裡但掃描說已離線 → `SREM`
- 掃描說在線但不在 SET 裡 → `SADD`

整份覆寫（`DEL` + 重建）有一個窗口讓 `SCARD` 讀到 0，而那個瞬間儀表板會顯示
「線上 0 人」——一個看起來像故障的正確操作。差集沒有這個窗口。

### D3：只在「狀態真正轉換」時動 SET

`markOnline` 已經回傳 `wasOffline`、`markOffline` 已經回傳 `nowOffline`——
這兩個布林正好是「該 `SADD`」與「該 `SREM`」的時機，不需要新的判斷。

**不要在每次 `heartbeat` 也 `SADD`。** 那看起來更安全（能自我修復漏掉的 SADD），
實際上是把每 15 秒一次的心跳變成每次都多一個 Redis 往返——
而心跳是所有 presence 操作裡頻率最高的那個。校正交給 sweep。

### D4：`SCARD` 的結果可能與 Hash 的真值短暫不一致，這是接受的

不一致的窗口有兩個：
- 實例被強制終止後，到下一次 sweep 之間（最多一個 sweep 週期）
- 差集校正與並行的連線／斷線之間（毫秒等級）

**對「儀表板上的在線人數」而言這完全可接受**：它回答的是「現在大概多少人」，
而不是任何授權或計費的依據。真正需要精確判斷的地方（`isOnline`）讀的是 Hash，
不受影響。

**要寫進 spec 的是「哪些用途不可以讀這個數字」**，而不是假裝它精確。

### D5：守則盯的是「誰可以掃」，不是「誰不可以掃」

`buildPresenceScanPattern` 的正當用途只有一個：sweep。
與其列舉所有不該用它的地方（那是無限的），不如**列舉可以用的地方**。

守則的形狀：任何**方法**只要用到那個 pattern，該方法就必須列入 allowlist 並註明理由。
判定以「方法名」為單位而非檔案，因為 adapter 本身既有 sweep 也有其他方法——
以檔案為單位會讓 `countOnlineMembers` 這次的錯直接漏掉。

這條規則要抓的不是今天這一個，是**下一個**——而下一個一樣不會有人在 review 時看見。

## Open Questions

- **sweep 週期是否要與儀表板的更新頻率對齊**：目前 sweep 綁 `WS_HEARTBEAT_INTERVAL`
  （預設 15 秒），儀表板推 5 秒。漂移最多存在 15 秒。要更準就得縮短 sweep，
  但 sweep 才是真正貴的那個操作——現在不動，等有實際的漂移抱怨再說。
- **SET 要不要加 TTL**：不加。它由 sweep 維護，而 sweep 只要服務活著就會跑；
  加了 TTL 反而製造「服務剛啟動時 SET 不存在」以外的第二種空窗。

## 為什麼不是「快取整份快照」

那是成本最低的改法（在 `DashboardStream` 側快取 30 秒），但它解決錯了問題：
它讓成本與**訂閱者數與 SSE 間隔**脫鉤，卻沒有動到「成本隨在線人數線性成長」。

而後者才是會咬人的那個——它的性質是「**使用者越多越糟**」，
而那種成本永遠在最不該出問題的時候出問題。
