## Context

三件都是 `tasks/todo.md` 裡標著「可以直接動」但一直沒動的項目。
不動的原因各不相同，而三個原因都是**同一種**：
**每一件的第一步都不是「開始改」，而是要先做出一個判斷**——
量哪個、擋在哪一層、要不要改語意。判斷做完之後動手都很小。

合成一支是因為三者各自太小，各開一支的 propose / PR / archive 成本
會高於實作本身。**但塊與塊之間完全沒有相依**，可以各自 commit、各自回退。

## Goals / Non-Goals

**Goals:**

- 營運快照的成本**可測量**，下一次決策有數據。
- `openspec validate --specs --strict` 全綠，且**不會再漂走**。
- 白名單啟用不當時**看得出來**，而且有恢復路徑。

**Non-Goals:**

- **不改任何索引、不加快取**（①的重點就是先不做這個）。
- **不改 IP guard 的 fail-closed**（③；理由見 D4）。
- 不改任何 requirement 的**語意**（②只動排版與敘述順序）。

## Decisions

### D1：①只量測，而且要量到「哪一個查詢」

快照有五個查詢：`countOnlineMembers` / `countByStatus` / `countRooms` /
`countUsers` / `countSince`。審查報告點名的是中間兩個，但**那是靜態推論**
（「沒有 WHERE」「沒有索引」），不是量出來的。

所以指標的標籤要是**查詢名**而不是「快照總耗時」——
總耗時只能告訴你慢，不能告訴你該修哪一個。
標籤是五個值的封閉集合，基數可控（`MetricsPort` 的既有約束：
標籤不得使用無界的值）。

**為什麼不先加索引**：三條路（`users` 加 `deletedAt` 索引 /
`chat_rooms` 加 `createdAt` 讓它 index-only scan / 整份快照快取 30 秒）
各有代價，而挑錯的成本高於多等一個週期。
`ResolveUserContextService` 已經示範過同樣的判斷。

### D2：②的七支 master spec 改動不走 delta spec

`openspec archive` 的 delta 機制要求 MODIFIED 貼上**整條** requirement
（含所有 scenario）。七條就是七份完整貼上，而**語意差異是零**——
改的是「把既有的 SHALL/MUST 從第二行移到第一行」。

貼七份只會製造雜訊：審閱者要逐字比對才能發現「其實沒改」。
因此本次直接修 `openspec/specs/`，並在 tasks.md 逐條列出改了哪七處，
讓 diff 自己說話。

⚠️ **這是刻意繞過 delta 流程，範圍嚴格限於「不改語意的排版」。**
判準：改完之後 requirement 的每一句話都還在，只是順序或斷行不同。
只要動到「規定了什麼」，就必須走 delta。

### D3：②的守則放在既有的 `openspec-spec-format.spec.ts`，不加進 verify:ci

兩個選項：

| 做法 | 涵蓋範圍 | 訊息品質 | 執行時機 |
| --- | --- | --- | --- |
| 加進 `openspec-spec-format.spec.ts` | 只有這條規則 | **指得出是哪一支 spec 的哪一條** | `pnpm test`（CI 已在跑） |
| 把 `openspec validate --specs --strict` 加進 `verify:ci` | openspec 所有規則 | 只說 `requirements.N` | 只有本機 `verify:ci` |

**兩個都做**，但主力是前者：它跑在 CI 既有的路徑上（不必新增 job），
而且錯誤訊息指得到人看得懂的位置。後者是廣撒的網，
接住未來 openspec 新增的其他規則——**否則修完還是會再漂走**，
而那正是這一項被列進待辦的原因。

### D4：③不改 fail-closed，改成「看得見 + 救得回」

「空白名單全鎖死」看起來像 bug，但**開啟白名單卻允許未列名的來源才是 bug**。
fail-closed 是對的。

真正的缺陷是兩件事：**沒有徵兆**（服務看起來正常，只是每個請求 403）
與**沒有恢復路徑**（能加白名單的 UI 自己也 403）。分別對應：

- **徵兆**：啟動時檢查一次，若「旗標開 + 清單為空」記 **error** 層級日誌，
  寫清楚後果與恢復方式。不是 warn——這個狀態下服務對使用者完全不可用。
- **恢復路徑**：seed 指令新增白名單項目，不必手動下 SQL。

**明確不做的三件**：

- ❌ **空清單就放行**——那讓開關形同虛設，是把安全功能改成裝飾。
- ❌ **啟動失敗**——#40 之後健康檢查會過，服務起得來；改成拒絕啟動會在
  k8s 變成 CrashLoopBackOff，把「設定錯誤」升級成「服務不存在」。
- ❌ **自動放行 loopback / 私有網段**——那是隱形的豁免，
  而本專案對豁免的判準是「必須明示且寫得比理由更窄」。

**啟動檢查只跑一次**是刻意的：這是設定錯誤，不是執行期狀態。
每次請求都查一次清單長度只會增加負擔而不增加資訊。
⚠️ 代價是**執行期把最後一筆刪掉不會有新的日誌**——記在需求裡，不假裝涵蓋。

## Risks / Trade-offs

- **①多一個指標的量測成本**。五個 `Date.now()` 差值，相對於查詢本身可忽略；
  且 `APPLICATION_METRICS_ENABLED=false` 時走 `NoopMetricsAdapter`。
- **②繞過 delta 流程**是這支最需要被監督的決定。緩解是把判準寫死在 D2，
  並在 tasks.md 逐條列出七處改動。
- **③的啟動日誌可能被忽略**——它跟其他啟動訊息混在一起。
  但「有一行 error」嚴格優於「什麼都沒有」，而更強的手段（拒絕啟動）
  的代價已在 D4 說明。
