## ADDED Requirements

### Requirement: IP 白名單啟用但清單為空時必須留下徵兆與恢復路徑

系統 SHALL 在啟動時檢查「IP 白名單已啟用且清單為空」，
命中時 MUST 記錄 **error** 層級的日誌，說明所有使用者流量將被拒絕、
以及如何恢復。

**這個狀態沒有徵兆且沒有出口。** guard 是 fail-closed，所以每一個請求都 403
——包含**能新增白名單的後台頁面本身**。服務看起來是活的
（健康檢查與指標端點已豁免，見 `platform-public-surface`），
但對使用者完全不可用，而**沒有任何東西說明為什麼**。

系統 SHALL 提供不經 HTTP 的方式新增白名單項目（seed 指令），
使管理者在被鎖在外面時仍能恢復。

**MUST NOT 以「清單為空就放行」解決。** 那讓開關形同虛設——
啟用了白名單卻允許未列名的來源，比不啟用更糟：它給出安全的錯覺。
同理 MUST NOT 自動放行 loopback 或私有網段：隱形的豁免違反
「豁免必須明示，且範圍要寫得比理由更窄」。

**MUST NOT 以拒絕啟動解決。** 服務起不來會在編排平台變成無限重啟，
把「設定錯誤」升級成「服務不存在」——那比一行 error 日誌更難診斷。

⚠️ **檢查只在啟動時執行一次。** 這是設定錯誤而非執行期狀態，
每個請求都查一次清單長度只增加負擔不增加資訊。
代價是**執行期刪掉最後一筆不會產生新的日誌**——這一點是知情的取捨。

#### Scenario: ⭐ 啟用白名單但清單為空

- **WHEN** 服務啟動時白名單功能已啟用，而清單沒有任何一筆
- **THEN** MUST 記錄 error 層級日誌，說明後果與恢復方式；
  服務 MUST 仍正常啟動

#### Scenario: 啟用白名單且清單非空

- **WHEN** 服務啟動時白名單已啟用且至少有一筆
- **THEN** MUST NOT 記錄該日誌

#### Scenario: 白名單功能關閉

- **WHEN** 白名單功能關閉
- **THEN** MUST NOT 檢查清單，也 MUST NOT 記錄該日誌

#### Scenario: ⭐ 以放行解決空清單

- **WHEN** 實作在清單為空時放行所有來源
- **THEN** 違反本需求——那使開關形同虛設
