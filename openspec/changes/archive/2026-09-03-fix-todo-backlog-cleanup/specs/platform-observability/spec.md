## ADDED Requirements

### Requirement: 營運快照的查詢成本必須可觀測

營運快照的**每一個查詢**SHALL 各自量測耗時並輸出為指標，
MUST NOT 只量整份快照的總耗時。

總耗時只說得出「慢」，說不出「該修哪一個」。而修法的選項
（加索引 / 改寫查詢 / 快取整份快照）代價各不相同，**選錯的成本高於多等一個週期**
——所以量測 MUST 先於最佳化。

指標的標籤 SHALL 是查詢名，且 MUST 是封閉集合
（本能力既有的約束：標籤不得使用無界的值，房間 ID 那類會讓時間序列無限增長）。

量測 MUST 經由 `MetricsPort`，application 層 MUST NOT 直接相依監控套件
（見「指標經 port 呼叫」）。指標關閉時 MUST 不產生額外成本。

**本需求不規定任何效能門檻或修法。** 它規定的是「做決定之前先有數據」——
快照掛在固定週期上（預設 5 秒）且首頁與營運總覽頁共用它，
成本會隨資料量成長，而**成長是無聲的**。

#### Scenario: ⭐ 只量總耗時

- **WHEN** 快照只輸出一個「總耗時」指標
- **THEN** 不滿足本需求——它指不出是哪一個查詢造成的

#### Scenario: 指標關閉時

- **WHEN** 指標功能關閉
- **THEN** 量測 MUST 不產生額外成本（走 no-op 實作）

#### Scenario: 標籤使用無界的值

- **WHEN** 指標以房間 ID、使用者 ID 這類無界的值作標籤
- **THEN** 違反本能力的標籤約束
