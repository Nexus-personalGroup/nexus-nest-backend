## Context

`add-chat-messaging` 已經把約束定下來了（見該 change 的 design.md「為之後的兩項預留了什麼」）：
撤回必須是軟刪除、`seq` 不能有洞、加 `deletedAt` 不需改動任何既有欄位。

這裡只補齊當時沒決定的部分，以及一個當時沒看到的風險：**內容遮蔽有三條讀取路徑**
（歷史查詢、斷線補齊、即時廣播），漏掉任何一條就是內容洩漏。

## Decisions

### D1：撤回走 REST，不走 WebSocket

`DELETE /api/front/chat-rooms/:roomId/messages/:messageId`，推播由 service 經
`EventPublisherPort` 送出。

**這與「送訊息走 WS」不矛盾，兩者的分工在本專案已經成形**：

| 走 WS | 走 REST |
| --- | --- |
| 即時訊息流：`sendMessage`、`syncRoom` | 狀態變更：`leaveRoom`、`markRead`、`retract` |

送訊息走 WS 的理由是狀態一致性（送出者不該有兩條路徑拿到同一則訊息）。撤回沒有這個問題：
它改的是一則**已經存在**的訊息，發起者拿到的是 204 而非一份新資料，
不存在「哪個先到」的競爭。而 REST 帶來的重試安全與冪等語意是白拿的。

**冪等**：重複撤回同一則訊息回 `204`，不是錯誤。撤回是收斂到某個狀態，
不是遞增操作——回 `409` 只會逼客戶端處理一個沒有意義的分支。

### D2：只有發送者本人可以撤回

沒有「房間管理員」的概念——`ChatRoomRecord.createdBy` 只是稽核欄位，不是角色。
在角色出現之前，任何「代替他人撤回」的入口都無法回答「憑什麼」。

後台管理員刪除違規訊息是**另一件事**：它的授權來自 RBAC、需要留稽核紀錄、
而且對使用者的語意是「被移除」而非「已收回」。那屬於 M3/M4，不在這裡。

### D3：時限進環境變數，預設 5 分鐘

`CHAT_RETRACT_WINDOW_SEC`，預設 300。

時限**以伺服器的 `createdAt` 為準**，不看客戶端時間——客戶端的時鐘不可信，
而這是個授權判斷。逾時回專屬錯誤碼，不與「不是你的訊息」共用：兩者都是發送者
自己的訊息，沒有洩漏疑慮，而分開才能給出可行動的提示。

### D4：內容保留、遮蔽發生在唯一的投影點

`retractedAt` 標記撤回時間，`content` **原封不動**。所有對外的訊息投影都經過
`PrismaChatMessageRepository.toMessage()`，遮蔽只寫在那裡一次。

**這是本 change 最容易出錯的地方。** 讀取路徑有三條——歷史查詢、斷線補齊、
即時廣播——漏掉任何一條，被撤回的內容就會從那條路徑流出去。而它不會有徵兆：
測試若只驗歷史查詢，補齊那條照樣洩漏。

因此：

- 遮蔽寫在 `toMessage()`，不寫在各個 service
- **新增守則**：`prisma.chatMessageRecord` 只能出現在該 repository（見下）
- 測試必須**逐條路徑**驗證，不能只驗一條就當作涵蓋

即時廣播那條實際上不會洩漏（新訊息不可能已被撤回），但仍納入測試——
「現在不可能」與「以後也不可能」是兩件事。

### D5：撤回後 `seq` 保留，訊息仍出現在補齊與歷史中

回傳的物件帶 `retractedAt`，`content` 為空字串。

**不能把該則從結果中濾掉。** 濾掉的話 `seq` 會出現洞，而客戶端無法區分
「這個號碼被撤回了」與「我漏收了」——後者會讓它反覆嘗試補齊同一段區間。

用空字串而非 `null`：`content` 目前是 `string`，改成可空會讓所有客戶端多一個
null 檢查，而它們本來就要判斷 `retractedAt` 才知道要顯示「訊息已收回」。

## Open Questions

- **撤回後的通知是否要送給已離開房間的人**：目前推播只到 socket room，
  離線者靠補齊拿到最新狀態。這在時限只有 5 分鐘時影響很小，暫不處理。
- **訊息保留期限**（沿用 `add-chat-messaging` 的未決項）：撤回的內容會與一般訊息
  一起無限保留。保留策略應與 M3 的檢舉功能一起決定。

## 為 M3 預留了什麼

`retractedAt` / `retractedBy` 兩個欄位就是檢舉調查要用的東西：
「這則訊息在被檢舉前多久被撤回」是判斷惡意的重要訊號。

M3 需要一個**後台專用**的讀取路徑來看到被撤回的內容。那條路徑必須繞過
`toMessage()` 的遮蔽——因此它會是新增守則的第一筆豁免，而豁免要註明
「僅限後台、需 RBAC 授權、且必須留稽核紀錄」。現在不做，但位置留好了。

## 實作過程中的修正

### 沒有引入 ClockPort，直接用 `Date.now()`

tasks.md 原本寫「單元測試用注入的時鐘或固定時間」，我一開始也真的加了 `ClockPort`。
但專案裡**沒有任何時鐘抽象**——既有的 `RefreshTokenService` 等都直接用 `Date.now()`，
測試以相對於現在的時間建 fixture。為了這一個 service 引入新抽象是過度設計。

改為：service 用 `Date.now()`，測試用 `secondsAgo(n)` 建 `createdAt`。時限是 5 分鐘，
測試偏移 10 分鐘，不存在時間敏感的不穩定性。

### `findByIdInRoom` 改名為 `findOwnership`，且不回傳內容

原本規劃的是「取得該訊息」。實作時發現撤回這條路徑只需要
「誰發的、何時發的、是否已撤回」三項——回傳完整訊息等於在**授權判斷之前**
就把內容取出來。改為 `findOwnership` 並在 `select` 中明確排除 `content`，
名稱也更誠實地說明它的用途。

### 撤回的原子性用 `updateMany` + 條件，不用讀-比-寫

`updateMany({ where: { id, retractedAt: null } })` 讓「尚未撤回時才寫入」在單一 SQL
內完成，受影響列數為 0 就代表早已撤回。這與已讀位置的
`ON CONFLICT ... WHERE` 是同一個模式：**狀態轉換的條件要寫在 SQL 裡**，
拆成讀-比-寫會讓並發的兩次撤回互相覆寫時間。
