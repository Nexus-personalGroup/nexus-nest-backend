## Context

兩項都在 `tasks/todo.md`「已知缺口（知情，非遺漏）」躺著，各自有寫下來的
「不做」理由。這支 change 推翻那兩個判斷，所以**先說清楚它們當初為什麼成立、
現在為什麼改**——否則下一個讀到舊理由的人會以為有人沒讀 todo。

- **TOCTOU**：當初的理由（「超一兩條沒有實質危害，修法複雜度不成比例」）
  在**風險**那一半仍然成立。改變的是**成本那一半**：查過 `PresenceConnection`
  的形狀之後發現它帶著 `instanceId` / `socketId` / `lastSeenAt`，
  足以做決定性的排序判斷，不需要新的 port 方法也不需要 Lua script（見 D1）。
- **全表掃描**：當初的理由是「要先確認搜尋語意」。**那是誤判**——
  `pg_trgm` 保留語意，沒有要決定的事（見 D3）。

## Goals / Non-Goals

**Goals:**

- 連線數上限是**上限**，不是建議值。
- `ILIKE '%x%'` 用得到索引，且**搜尋語意一個字都不變**。
- 兩項的行為都寫進 spec——它們目前都只存在於程式碼。

**Non-Goals:**

- 不改搜尋語意（不改成前綴搜尋、不引入全文檢索）。
- 不動 `members` 側的搜尋（見 D4）。
- 不追求「上限的絕對精確」——見 D2 的殘留競態。

## Decisions

### D1：寫入後回讀 + 決定性排序，而不是分散式鎖

最直覺的修法是加鎖（Redis SETNX），但那是**為了一個上限值付出分散式鎖的代價**：
鎖要有 TTL、要處理持鎖者當機、要決定等待策略，而它保護的東西是「最多開幾個裝置」。

選的做法是**寫入後回讀**：

1. 維持既有的預先檢查（快路徑，常見情況下省掉一次寫入）。
2. `markOnline` 寫入自己的欄位。
3. 重新 `getConnections()`，此時清單**包含自己**。
4. 依 `lastSeenAt` 升冪、同值時以 `instanceId:socketId` 字串為次鍵排序。
5. 找出自己的索引；`>= 上限` 就 `markOffline` 撤掉自己並拒絕。

**次鍵排序是關鍵**，不是防禦性程式碼：兩條連線同一毫秒寫入時 `lastSeenAt` 會相同，
沒有次鍵的話兩個實例可能得到不同的排序，於是**兩條都認為自己超額而互相禮讓**
（結果少一條連線），或**兩條都認為自己沒超額**（結果多一條）。
字串次鍵讓所有實例對同一份 Redis 狀態得到同一個答案。

**不選「只比較數量」**：`connections.length > limit` 時所有超額者都會看到同樣的
真值，於是同時進來的兩條會**都被拒絕**——本來只該拒一條。

### D2：接受一個殘留競態，並寫進 spec

回讀之間仍有窗口：A 寫入 → B 寫入 → A 回讀（看到 2）→ B 回讀（看到 2）。
兩者都算得出正確的位置，所以這個順序是安全的。**不安全的是**：
A 寫入 → A 回讀（位置 9，通過）→ B 寫入 → 現在共 11 條，而 A 已經放行。
下一條連線會看到 11 並拒絕，但那 11 條會存續到有人斷線為止。

**接受它。** 要消掉得靠原子操作（Lua script 把「寫入 + 計數 + 回滾」包成一次），
而那會把 presence 的儲存格式綁進腳本裡。上限的用途是防止單一帳號無限開連線，
超額幾條、且會隨斷線自然收斂，與那個目的沒有衝突。

**寫進 spec 而不是只寫註解**：一個「幾乎精確」的上限，下一個人量到 11 條時
會以為是 bug。寫下來讓他知道那是已知且刻意的。

### D3：`pg_trgm` GIN，索引宣告在 schema.prisma，extension 建在 migration

`pg_trgm` 的 GIN 索引可以加速 `ILIKE '%x%'`，**且不改變比對語意**——
這是它比「改成前綴搜尋」好的地方：後者要動搜尋行為（使用者輸入
`@gmail.com` 就找不到人了），而那才是需要產品決定的事。

分工要正確，否則會被 Prisma 弄掉：

| 東西 | 放哪 | 為什麼 |
| --- | --- | --- |
| `CREATE EXTENSION pg_trgm` | migration SQL | 沒開 `postgresqlExtensions` preview 時 Prisma 不管 extension，寫在 migration 不會造成 drift |
| 兩個 GIN 索引 | **`schema.prisma`** | 只寫在 migration 裡的話，Prisma 比對 schema 與 migration 產生的 shadow DB 會看到「DB 有、schema 沒有」的索引，**下一次 `migrate dev` 會產生一支把它刪掉的 migration** |

**已知限制要寫進 spec**：pg_trgm 以三字元為單位建索引，
**搜尋字串少於 3 個字元時索引用不上**，仍會退回全表掃描。
不寫的話下一個人量到「搜 `ab` 還是很慢」會以為索引沒建成功。

**不選 `postgresqlExtensions` preview feature**：它能把 extension 宣告進 schema，
但要開 preview flag，而本專案只需要一個 extension、一次性建立。
用 preview 換一行宣告不划算。

### D4：不動 `members` 側的搜尋

`members` 是後台帳號表，量級與 `users` 差好幾個數量級（一個是同事、
一個是客戶名單），而且後台帳號列表的使用頻率遠低於前台會員列表。
**沒有實測依據就不加索引**——每個索引都有寫入成本，而這裡連「慢」都還沒發生。
要動時同樣的做法照搬即可。

## Risks / Trade-offs

- **`CREATE EXTENSION` 需要權限。** 本地與 CI 是 superuser，正式環境若不是會失敗。
  用 `IF NOT EXISTS`，讓 DBA 先建好之後 migration 仍可跑過。
- **GIN 索引有寫入成本。** `users` 的寫入是註冊與偶爾的個資更新，
  相對於搜尋的頻率可以忽略；但這是根據使用模式的推論，不是實測。
- **回讀多一次 Redis 往返。** 只發生在連線建立時，不在訊息路徑上。
- **殘留競態沒有消掉**（見 D2）。
