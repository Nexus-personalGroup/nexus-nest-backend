## Context

審查報告的結論值得引用，因為它決定了這支 change 的性質：

> 剩下的建議幾乎都是**把已經做對的判斷寫到會被讀到的地方**。
> 這種階段的專案，文件的邊際價值已經高過程式碼了。

六個項目沒有一個是行為缺陷。但它們各自會讓下一個人推論錯誤——
而錯誤的推論比缺陷更難修，因為沒有東西會失敗。

## Goals / Non-Goals

**Goals:**

- 註解指向的東西真的存在。
- nginx 的設定可以被當成正式拓撲的樣板抄過去而不帶著坑。
- 兩種守則手段的守備範圍寫在 `testing.md`，而不是靠每次重新想。

**Non-Goals:**

- **不做審查報告的問題 1**（營運快照的無界 `COUNT(*)`）——見 D4。
- 不動 nginx 的路由本身，只動 upgrade 標頭與註解。
- 不改任何測試的斷言（本支不修行為，除了 Swagger 日誌與 `Connection` 標頭）。

## Decisions

### D1：nginx 用 `map`，而不是在三個 location 各寫一次條件

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
```

`map` 在 `http` 區塊定義一次，三個 `location` 各用一行引用。
替代方案是每個 location 用 `if` 判斷——nginx 的 `if` 在 `location` 內
有惡名昭彰的求值陷阱（官方 wiki 的「If Is Evil」），而 `map` 是為這件事設計的。

**為什麼現在改**：目前兩個 `upstream` 都沒有 `keepalive`，所以不重用上游連線，
畸形的 `Connection: upgrade` 不會造成可觀察的問題。**但這正是要現在改的理由**
——它是一個「加了效能設定才會咬人」的坑，而咬人的時候症狀是
「加了 keepalive 但沒有變快」，沒有任何東西會失敗。

### D2：nginx 註解要寫「哪些不該從外面進來」，不只是「別漏掛」

檔頭現在寫著：

> 加後端路由前先確認它落在 `/api` 或 `/socket.io` 底下。

那是**漏掛**的防線。缺的是反向的：`/api/metrics`（`JwtAuthGuard` 明確豁免認證）
與 `/api/admin/docs-json`（完整後台結構）在正式環境需要排除或另行保護。

dev 綁 `127.0.0.1` 且 `APPLICATION_METRICS_ENABLED` 預設關閉，所以現在無害。
**但這份檔案自己宣告了它是正式拓撲的樣板**（檔頭：「讓開發時的拓撲與正式的
單一埠部署一致」），而樣板會被抄。

**只加註解不加 `location` 封鎖**：dev 環境需要打得到 `/api/admin/docs`，
封鎖了會擋掉日常使用。真正的封鎖屬於正式環境的設定，而那份設定還不存在——
現在做等於為一個沒有形狀的東西寫規則。

### D3：兩種守則手段的守備範圍要並列，因為它們互補而非替代

審查報告點出這一招（讀原始碼字面值的守則）的邊界，值得原樣寫進 `testing.md`：

| 讀字面值的守則擋得住 | 擋不住 |
| --- | --- |
| 兩處常數漂移（一邊加了、另一邊沒加） | **值本身是錯的**（兩邊一致地錯） |
| 守衛被移除或註解掉 | 守衛還在但語意變了 |
| 死字串（權限碼移除後遺留的對照） | 執行期行為 |

第二輪的 🔴 1（驗證信連結拿 `APP_FRONT_URL` 當後端 base）正是「兩邊一致地錯」，
而 `testing.md` 已經有一節在講它（「測不到的形狀：送到系統外面去的字串」），
解法是**直接斷言輸出**。

**兩節要互相指向**：目前它們各自存在，讀到其中一節的人不會知道另一半。
一個新問題該用哪一招，取決於「錯的是兩處不一致，還是值本身」——
那個判準要寫下來。

### D4：不做問題 1，而且理由要寫下來

營運快照每 5 秒跑兩個無界 `COUNT(*)`，而 #30 把它接到了首頁。
報告給了三條路（加索引 / 快照快取 / 先加觀測），並明說：

> **不要在還沒量之前就選方案**——那是這個專案自己在 `ResolveUserContextService`
> 示範過的判斷。

所以它需要先加觀測直方圖、跑一段時間、再決定。那是一支獨立的 change，
與本支「文件與設定」的性質完全不同，混在一起會讓兩者都做不好。
**已記進 `tasks/todo.md`**，不是忘記。

### D5：`VERIFY_DB_PORT` 與根目錄 `.env.example`

`15432` 寫死在兩處（`compose.yml` 與 `scripts/verify-ci.sh`），而其他三個對外埠
都能用根目錄 `.env` 覆寫。不一致本身不痛（那個埠只在驗證時開、跑完即拋），
但它讓「對外埠都可以調」這句話變成**大部分正確**，而那種話最難用。

順帶發現：**根目錄根本沒有 `.env.example`**。於是「有哪些可以調」只能去讀
`compose.yml` 的 `${...}`，而 README 只列了變數名沒有給檔案。補一份，
並在檔頭寫清楚它與 `apps/api/.env` 的分工——那是這個專案最容易搞混的一組設定
（README 已經為此寫過一個 blockquote 警告，但沒有檔案可以對照）。

## Risks / Trade-offs

- **Swagger 日誌包進 `if` 之後，關閉時完全沒有痕跡。** 這是對的
  （關掉就不該宣告一個 404 網址），但如果有人以為 Swagger 開著卻找不到日誌，
  會多花一分鐘。可接受——`SWAGGER_ENABLED` 的值本來就該由設定確認，不是由日誌。
- **`map` 指令必須放在 `http` 區塊**，而本檔是 `conf.d/*.conf`（已在 `http` 內），
  所以直接寫在 `server` 之外即可。放錯位置 nginx 會啟動失敗——
  這一點會在實機驗收時立刻顯現，不是靜默問題。
- **新增 `VERIFY_DB_PORT` 而 CI 不會設它**，走預設 15432，行為不變。
