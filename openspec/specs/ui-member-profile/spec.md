# ui-member-profile Specification

## Purpose

定義成員概覽頁（`/moderation/members/:memberId`）的行為：它把一個人散在
檢舉、聊天室、行為紀錄裡的資料收攏成一頁，回答「這個人到底做過什麼」。

**它沒有列表可以進入，只能帶著 ID 過來。** 這不是還沒做，是刻意的——
審閱人員看不到成員清單（那需要帳號管理權限），所以 Sidebar 上
**不會有這一項**：一個點進去只會看到「請提供 ID」的選單項目比沒有更糟。
入口是檢舉詳情頁的「檢舉人」與「被檢舉人」連結。

同樣因為是被帶進來的，**返回不得寫死回檢舉佇列**——使用者多半是從某一筆
檢舉詳情過來的，跳回佇列會弄丟他的位置。

兩個容易做錯的呈現細節，都關於「這個數字是什麼時候的」與「這兩個數字不一樣」：

- **在線狀態是查詢當下的，不輪詢**，因此必須標明；不標的話使用者會以為它是即時的，
  然後在它不變時懷疑系統壞了。
- **被檢舉次數與提出檢舉次數必須分開**，合併成一個「檢舉相關」總數會把
  意義相反的兩件事加在一起。

任何區塊都**不顯示訊息內容**——與 `ui-room-overview` 同一條界線：
這是審閱動線，不是訊息瀏覽器。

## Requirements
### Requirement: 成員概覽頁的路由與進入點

`apps/web/` SHALL 提供 `/moderation/members/:memberId` 成員概覽頁。

- 路由 MUST 受 `RequireAuth` 保護，未登入導向 `/login`。
- 使用者沒有 `BACKEND:MODERATION:VIEW` 權限時 MUST 導向 `/`，且 MUST NOT 發出任何 API 請求。
- **Sidebar MUST NOT 新增此頁的項目**：概覽頁沒有列表可以進入——
  審閱人員看不到成員清單（那需要帳號管理權限），一個點進去只會看到「請提供 ID」
  的選單項目比沒有更糟。
- 檢舉詳情頁的「檢舉人」與「被檢舉人」MUST 成為連往各自概覽頁的連結。
- 概覽頁 MUST 提供返回上一頁的方式，且**不得寫死回檢舉佇列**——
  使用者可能是從某一筆檢舉詳情過來的，直接跳回佇列會弄丟他的位置。

#### Scenario: 從檢舉詳情點進當事人

- **WHEN** 管理員點檢舉詳情頁的「被檢舉人」
- **THEN** 導向 `/moderation/members/<該成員 id>`

#### Scenario: 無權限直接打 URL

- **WHEN** 沒有 `BACKEND:MODERATION:VIEW` 的使用者輸入該網址
- **THEN** 導向 `/`，不發出任何請求

#### Scenario: 側邊欄沒有這一項

- **WHEN** 檢視 Sidebar
- **THEN** MUST NOT 出現「成員概覽」之類的項目

### Requirement: 概覽頁的區塊組成

概覽頁 SHALL 由五個區塊組成：基本資料、檢舉統計、聊天室清單、相關檢舉列表、行為時間軸。

- **基本資料**：email、啟用狀態、加入時間、在線狀態。
  帳號已停權時 MUST 明顯標示（不只是一個「停用」文字）。
- **在線狀態 MUST 標明它是查詢當下的狀態**，MUST NOT 輪詢或訂閱更新。
  不標示的話使用者會以為它是即時的，然後在它不變時懷疑系統壞了。
- **檢舉統計**：被檢舉次數與提出檢舉次數並列，兩個數字 MUST 分開顯示，
  MUST NOT 合併成一個「檢舉相關」的總數——兩者的意義相反。
- **聊天室清單**：房間名稱（私聊顯示為「私聊」）、成員數、**房間建立時間**，分頁。
  顯示的不是該成員的加入時間——共用的查詢沒有那個欄位，
  而為了它改共用的回應形狀，代價會落到前台身上。
- **相關檢舉列表**：可切換「被檢舉」與「提出的」，每一列可點進該筆檢舉詳情。
- **行為時間軸**：複用檢舉詳情頁的同一個元件。

任何區塊 MUST NOT 顯示訊息內容——概覽的端點本來就不回，前端也不從其他來源補。

#### Scenario: 檢視一個被檢舉多次的成員

- **WHEN** 管理員從檢舉詳情點進被檢舉人
- **THEN** 五個區塊都顯示，被檢舉次數反映實際筆數

#### Scenario: 已停權的成員

- **WHEN** 該成員的 `status` 為 `false`
- **THEN** 基本資料區塊明顯標示已停權

#### Scenario: 成員不存在

- **WHEN** 網址中的 `memberId` 查不到
- **THEN** 顯示「成員不存在」與返回的方式，MUST NOT 顯示空白畫面

#### Scenario: 沒有任何聊天室

- **WHEN** 該成員不在任何房間
- **THEN** 該區塊顯示空狀態，MUST NOT 顯示錯誤

### Requirement: 相關檢舉的方向切換

相關檢舉列表 SHALL 提供「被檢舉」與「提出的」兩個方向的切換。

- 預設 MUST 為「被檢舉」——那是審閱的主要問題。
- 切換 MUST 同步到 URL query，重新整理後保持。
- 每一列 MUST 顯示**對造**的 email（而非重複顯示這個人自己），
  email 為 `null` 時比照佇列顯示「已刪除的帳號」與 id 尾碼。
- 點任一列 MUST 導向該筆檢舉的詳情頁。

#### Scenario: 切到「提出的」

- **WHEN** 管理員切換方向
- **THEN** 重新查詢並把 `role=REPORTER` 寫進 URL query，列表顯示被檢舉人的 email

#### Scenario: 從概覽點回檢舉詳情

- **WHEN** 管理員點相關檢舉的某一列
- **THEN** 導向 `/moderation/reports/<該筆 id>`，並在該處寫入一筆 `REPORT_VIEWED` 稽核

### Requirement: 概覽頁不得預先載入檢舉詳情

概覽頁列出的是檢舉的**摘要**，點進詳情才會看到內容快照並留下稽核。

- 相關檢舉列表 MUST NOT prefetch 任何一筆的詳情（含 hover 預載）。
- 概覽本身的查詢不寫稽核，因此 MUST NOT 為了「省一次請求」而改用詳情端點取資料。

#### Scenario: 在相關檢舉列表上 hover

- **WHEN** 滑鼠移過某一列
- **THEN** MUST NOT 發出該筆的詳情請求
