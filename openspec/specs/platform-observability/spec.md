# platform-observability Specification

## Purpose
聊天系統的可觀測性：Prometheus 指標與行為稽核。

兩者都無法回溯補齊——沒有埋點就永遠不知道上週的峰值，
沒有稽核就永遠不知道某人在被檢舉前做了什麼。因此它們必須先於介面存在。

貫穿全篇的兩個判準：

- **稽核記什麼**：判準是「這件事發生過的證據會不會消失」，不是「這件事重不重要」。
  送出訊息不記——`chat_messages` 已是它自己的紀錄；離開房間要記——
  成員關係列被直接刪除，那件事過去之後不留任何痕跡。
- **指標怎麼分類**：標籤只用封閉集合。房間 ID 這類無界的值會讓時間序列無限增長，
  那是監控系統最典型的自傷方式。

稽核是 best-effort：失敗不得讓業務動作失敗，但**必須看得見**（error 等級記錄），
而不是 fire-and-forget 那種完全無聲的丟失。
## Requirements
### Requirement: 聊天行為稽核只記錄無法回溯的行為

系統 SHALL 為「證據會隨著資料變動而消失」的聊天行為留下稽核紀錄，
MUST NOT 為已有既存紀錄的行為（例如送出訊息）另外寫一筆。

判準是「這件事發生過的證據會不會消失」，不是「這件事重不重要」。
送出訊息已經記在 `chat_messages`（發送者、房間、時間、序號），
再寫一筆稽核只是把同一份中繼資料存兩次，代價是熱路徑多一次寫入與儲存翻倍。

MUST 稽核的行為至少包含：加入房間、離開房間、撤回成功、撤回被拒、被限流擋下、
提出檢舉、查看檢舉詳情、管理員移除訊息、管理員還原訊息、
**停權成員**、**解除停權**。

**停權與解除都要記**，理由與移除／還原相同：`members.status` 只留下「現在是什麼狀態」，
留不下「誰在什麼時候改的」——而**反覆停權再解除本身就是可疑行為**，
只有兩邊都記才看得出那個模式。

管理員的所有處置動作與查看檢舉詳情同屬**權力的行使**：權力要留下痕跡，
否則它就只是一個沒有人在看的開關。

稽核紀錄 MUST NOT 包含訊息內容。內容已存在於 `chat_messages`（撤回與移除都保留），
複製一份等於多一條洩漏路徑，而且兩份內容的遮蔽規則必須同步維護。

#### Scenario: 成員離開房間

- **WHEN** 某成員離開房間，成員關係列被刪除
- **THEN** 留下一筆稽核紀錄，包含成員、房間、時間

#### Scenario: 送出訊息

- **WHEN** 成員成功送出一則訊息
- **THEN** MUST NOT 寫入稽核紀錄——`chat_messages` 已是它自己的紀錄

#### Scenario: 被限流擋下

- **WHEN** 送訊息因超過限流而被拒
- **THEN** 留下稽核紀錄——這是洗版行為的唯一證據

#### Scenario: 提出檢舉

- **WHEN** 成員成功提出一筆檢舉
- **THEN** 留下稽核紀錄，含檢舉人與被檢舉的訊息

#### Scenario: 管理員查看檢舉詳情

- **WHEN** 管理員讀取單筆檢舉（因而看到內容快照）
- **THEN** 留下稽核紀錄，含管理員與該筆檢舉

#### Scenario: 管理員瀏覽檢舉列表

- **WHEN** 管理員讀取檢舉列表
- **THEN** MUST NOT 寫入稽核——列表不含內容快照，沒有看到任何敏感內容

#### Scenario: 管理員移除訊息

- **WHEN** 管理員移除一則訊息
- **THEN** 留下稽核紀錄，含管理員、被移除訊息與其發送者

#### Scenario: 管理員還原訊息

- **WHEN** 管理員還原一則被移除的訊息
- **THEN** 留下稽核紀錄——`removedAt` 清除後，那件事發生過的證據只剩稽核

#### Scenario: 停權成員

- **WHEN** 某成員被停權（不論從哪個入口）
- **THEN** 留下稽核紀錄，含執行的管理員與被停權者

#### Scenario: 解除停權

- **WHEN** 某成員的停權被解除
- **THEN** 留下稽核紀錄——`status` 只留下現在的狀態，留不下誰在何時改的

#### Scenario: 稽核紀錄不含內容

- **WHEN** 任何稽核紀錄被寫入
- **THEN** 其欄位中 MUST NOT 出現訊息內容

### Requirement: 稽核寫入失敗不得影響業務動作

稽核寫入 SHALL 為 best-effort：失敗時 MUST NOT 讓觸發它的業務動作失敗，
且 MUST 以 error 等級記錄。

稽核表滿了或寫入逾時，不該讓使用者送不出訊息或離不開房間。

但**失敗必須看得見**：MUST NOT 使用 fire-and-forget（未處理的 Promise 會變成
unhandled rejection，且失敗完全無聲）。立場是「盡力而為，但失敗要留下痕跡」。

#### Scenario: 稽核寫入拋錯

- **WHEN** 稽核 port 的寫入失敗
- **THEN** 業務動作照常完成，錯誤以 error 等級記錄

#### Scenario: 稽核關閉

- **WHEN** 稽核開關關閉
- **THEN** 不寫入任何紀錄，業務動作不受影響

### Requirement: 指標經 port 呼叫，application 層不得相依監控套件

業務服務 SHALL 透過 `MetricsPort` 回報指標，MUST NOT 直接 import `prom-client`
或其 NestJS 包裝。

服務要能說「訊息送出了」，但不該知道那是 counter 還是 histogram——
換掉監控實作時不該動到任何業務程式碼。

指標的標籤 MUST NOT 使用無界的值（例如房間 ID）。
標籤基數爆炸是監控系統最典型的自傷方式。

#### Scenario: service 直接使用 prom-client

- **WHEN** application 層的檔案 import `prom-client`
- **THEN** 違反本需求，MUST 由架構守則在測試階段攔截

#### Scenario: 以房間 ID 作為標籤

- **WHEN** 指標以房間 ID 為標籤
- **THEN** 違反本需求——房間數無界，時間序列會無限增長

### Requirement: 指標與稽核必須各自獨立開關

指標與稽核 SHALL 由各自的環境變數控制，MUST NOT 共用同一個開關。

兩者的失效模式不同：指標關掉只是看不到趨勢，稽核關掉會讓日後的調查沒有依據。
共用開關會讓「暫時關掉指標降低負載」這個合理操作順手把稽核也關了，
而那要等到真的需要調查時才會發現。

#### Scenario: 關閉指標

- **WHEN** 指標開關關閉、稽核開關開啟
- **THEN** 不曝露自訂指標，但稽核照常寫入

### Requirement: 安全防護的降級必須可觀測

在相依服務不可用時**選擇放行**的安全防護路徑 MUST 記錄警告層級的日誌，
且 MUST 有對應的指標。靜默放行 MUST 視為違反本需求。

**這條守的不是「該不該降級」，是「降級了有沒有人知道」。**
登入失敗計數與 IP 失敗計數在 Redis 不可用時回 0，
於是「失敗次數達到門檻」永遠不成立——帳號鎖定與 IP 黑名單**整組不會觸發**。
那是刻意的 graceful degradation，本需求不推翻它；問題在於它**完全沒有痕跡**：
Redis 掛掉的期間可以無限次猜密碼，而事後翻日誌也看不出那段時間發生過什麼。

方向的不一致才是真正值得記錄的地方：同一個 Redis client，
認證路徑（`isBlacklisted`）選 **fail-closed**——不可用就整站 503；
暴力破解防護選 **fail-open**——不可用就不擋。兩個方向相反的選擇各自都可辯護，
但**沉默的那一邊風險更高**：503 會有人立刻發現，靜默放行不會。

指標 MUST 能區分「降級發生了幾次」與「正常路徑跑了幾次」，
否則無法回答「上週那波登入嘗試是在防護有效還是失效的時候發生的」。

#### Scenario: Redis 不可用時記錄一次失敗登入

- **WHEN** `recordFailedLogin` 在 Redis 不可用時被呼叫
- **THEN** MUST 輸出警告日誌，MUST 遞增降級指標，且 MUST 仍然回傳（不阻塞登入流程）

#### Scenario: Redis 不可用時記錄一次 IP 失敗

- **WHEN** `recordFailedIpAttempt` 在 Redis 不可用時被呼叫
- **THEN** 行為同上——兩條路徑 MUST NOT 只做其中一條

#### Scenario: Redis 正常時

- **WHEN** Redis 可用
- **THEN** MUST NOT 輸出降級警告，MUST NOT 遞增降級指標

#### Scenario: 新增一條會降級的防護路徑

- **WHEN** 日後新增的防護在相依不可用時選擇放行，但沒有日誌也沒有指標
- **THEN** 違反本需求

### Requirement: 營運快照的查詢成本必須可觀測

營運快照的**每一個查詢**SHALL 各自量測耗時並輸出為指標，
MUST NOT 只量整份快照的總耗時。

總耗時只說得出「慢」，說不出「該修哪一個」。而修法的選項
（加索引 / 改寫查詢 / 快取整份快照）代價各不相同，**選錯的成本高於多等一個週期**
——所以量測 MUST 先於最佳化。

指標的標籤 SHALL 是查詢名，且 MUST 是封閉集合
（本能力既有的約束：標籤不得使用無界的值，房間 ID 那類會讓時間序列無限增長）。

量測 MUST 經由 `MetricsPort`，application 層 MUST NOT 直接相依監控套件
（見「指標經 port 呼叫」）。指標關閉時 MUST 不產生額外成本。

**本需求不規定任何效能門檻或修法。** 它規定的是「做決定之前先有數據」——
快照掛在固定週期上（預設 5 秒）且首頁與營運總覽頁共用它，
成本會隨資料量成長，而**成長是無聲的**。

#### Scenario: ⭐ 只量總耗時

- **WHEN** 快照只輸出一個「總耗時」指標
- **THEN** 不滿足本需求——它指不出是哪一個查詢造成的

#### Scenario: 指標關閉時

- **WHEN** 指標功能關閉
- **THEN** 量測 MUST 不產生額外成本（走 no-op 實作）

#### Scenario: 標籤使用無界的值

- **WHEN** 指標以房間 ID、使用者 ID 這類無界的值作標籤
- **THEN** 違反本能力的標籤約束
